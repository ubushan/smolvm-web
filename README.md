# smolvm-web

Веб-интерфейс для [smolvm](https://github.com/smol-machines/smolvm): управление microVM из браузера поверх локального HTTP API (`smolvm serve`).

Без зависимостей и сборки: Node.js ≥ 18 (для сертификатов из хранилища ОС — ≥ 22.15) и установленный `smolvm`.

## Запуск

**macOS / Linux**

```bash
./start.sh                     # = node server.js --autostart
```

**Windows** (cmd или PowerShell)

```bat
start.cmd
```

`--autostart` сам поднимает `smolvm serve`, если он не отвечает. Откройте <http://127.0.0.1:7777>.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SMOLVM_API` | macOS/Linux: `unix:///tmp/smolvm.sock`<br>Windows: `http://127.0.0.1:18899` | адрес `smolvm serve` |
| `SMOLVM_BIN` | `smolvm` | путь к бинарнику (`C:\tools\smolvm.exe`) |
| `PORT` | `7777` | порт веб-интерфейса |
| `SMOLVM_AUTOSTART` | — | `1` = то же, что `--autostart` |
| `SMOLVM_WEB_EGRESS_PORT` | `7791` | порт egress-фильтра (allow list) на хосте |
| `SMOLVM_WEB_HOME` | `~/.config/smolvm-web`, Windows: `%APPDATA%\smolvm-web` | настройки и лог `smolvm-serve.log` |

### Windows

- smolvm на Windows не поддерживает Unix-сокет, поэтому API слушает loopback TCP `127.0.0.1:18899`. Нужна включённая Windows Hypervisor Platform.
- Вывод `smolvm serve` и `smolvm machine start` пишется в файл, а не в pipe: на Windows CLI иначе не возвращает управление.
- Монтирования принимают пути с буквой диска: `C:\Users\me\project:/work` или `D:/data:/data:ro`.
- «Определить автоматически» берёт системный прокси из `Internet Settings` (реестр), сертификаты — из хранилища Windows.

## Возможности

- **Профили и агенты**: Claude Code, OpenCode, DeepSeek Harness — установка одним кликом, агент открывается в новой вкладке браузера.
- **Машины**: список с автообновлением, создание (образ, ресурсы, сеть, порты, env, монтирования, egress allow-list, restart policy), старт / branchable-старт, стоп, пауза / возобновление, ветки (copy-on-write клон), удаление.
- **Консоль**: потоковый вывод `exec/stream`, сохранение текущей директории, история, выбор пользователя, Ctrl+C / Ctrl+L.
- **Логи** (follow/tail), **файлы** (навигация, скачивание, загрузка drag-and-drop), **образы** (список, pull), **egress**-блокировки, загрузка хоста.
- **Доступ в сеть** — allow list ресурсов для машин: фильтрующий прокси на хосте, списки правил, жёсткая изоляция.
- **Журнал** — отдельная страница со всеми соединениями машин через фильтр, фильтрами по машине/решению/хосту и кнопкой «Разрешить».
- **Директории** — разрешённые директории хоста и права (запись / чтение / нет доступа) для конкретных пользователей внутри машины.

## Корпоративный прокси

Кнопка **⚙** (или индикатор в шапке) → «Сеть, прокси и сертификаты».

| Что | Как реализовано |
|---|---|
| Запуск и образы | При включённом прокси машина стартует через `smolvm machine start [--proxy … --no-proxy …]`: HTTP API smolvm при старте тянет образ без прокси, а `smolvm serve` ставит строгую egress-политику (`SMOLVM_EGRESS_FLOOR=strict`), при которой машины не видят хост и LAN — то есть и корпоративный прокси. Pull во вкладке «Образы» получает поле `proxy`. |
| Переменные в машине | `HTTP(S)_PROXY`, `NO_PROXY` (в обоих регистрах) добавляются в `env` при создании и в каждый `exec` из консоли/API. Явно заданные переменные не перезаписываются. |
| Настройка гостя после старта | `/etc/profile.d/smolvm-proxy.sh`, `/etc/pip.conf`, глобальный `npmrc`, `/etc/apt/apt.conf.d/95smolvm-proxy`, `git config --system http.proxy`. Для уже запущенной машины — кнопка «Применить прокси». |
| Прокси на `localhost` хоста (cntlm, px) | Внутри машины `localhost` — это сама машина, поэтому адрес переписывается на IP хоста. Прокси должен слушать этот интерфейс (`Gateway yes` в cntlm, `--gateway` в px). |
| TLS-инспекция | Bundle = публичные корневые (Mozilla) + сертификаты ОС + ваш PEM/файл. Кладётся в `/etc/smolvm-host-trust/ca-bundle.pem`, на него указывают `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `GIT_SSL_CAINFO` и др.; опционально заменяет системный bundle гостя (apk, apt, curl, wget). |
| Проверка | «Проверить» делает `CONNECT` к docker.io / pypi.org / npmjs.org через прокси с хоста и по адресу, который увидят машины. |
| Исключения | NO_PROXY общий; на отдельной машине прокси можно выключить (вкладка «Обзор» или чекбокс при создании). |

Если `smolvm serve` запускается через `--autostart` при включённом прокси, ему тоже передаются `HTTPS_PROXY`/`NO_PROXY` (запросы к реестрам со стороны хоста). После изменения прокси перезапустите smolvm-web, чтобы это применилось.

Альтернатива для образов — зеркало реестра (Nexus/Artifactory) в `~/.config/smolvm/registries.toml` (`mirror = "…"`).

Ограничения: PAC-файлы не поддерживаются (укажите адрес прокси явно); логин/пароль в URL прокси видны процессам внутри машины.

## Секреты и API-ключи

Ключ (DeepSeek, OpenAI, GitHub…) хранится в зашифрованном хранилище на хосте, а агент в машине может им **пользоваться, но не может его прочитать**. Значение не попадает ни в машину, ни в её запись в smolvm, ни в интерфейс (после сохранения оно не показывается).

| Режим | Что видит машина | Как работает | Когда |
|---|---|---|---|
| **Шлюз smolvm-web** | `DEEPSEEK_API_KEY=smolgw_…` (токен машины), `DEEPSEEK_BASE_URL=http://<IP хоста>:7790/g/deepseek` | SDK шлёт запрос на шлюз; шлюз проверяет токен, меняет его на ключ и отправляет на `https://api.deepseek.com` — **через корпоративный прокси**, если он настроен | По умолчанию за прокси |
| **Подстановка smolvm** | `DEEPSEEK_API_KEY=SMOL_PLACEHOLDER_…` | Родной [credential substitution](https://github.com/smol-machines/smolvm/blob/main/docs/credential-substitution.md): хост подменяет заглушку в HTTPS-заголовке, только к указанным хостам. Значения передаются в `smolvm serve` (`PUT /credential-values`) перед каждым стартом | Есть прямой интернет. Перехватчик smolvm ходит к API **без прокси** — за корпоративным прокси не работает |
| **Переменная** | значение как есть | Добавляется в команды консоли/exec | Только то, что программа должна прочитать сама (URL БД) |

Пример для агента (OpenAI-совместимый SDK, DeepSeek):

```python
from openai import OpenAI
import os
client = OpenAI(base_url=os.environ["DEEPSEEK_BASE_URL"], api_key=os.environ["DEEPSEEK_API_KEY"])
```

Как пользоваться: «Секреты» → «+ Добавить» (есть шаблоны DeepSeek/OpenAI/Anthropic/OpenRouter/Gemini/GitHub) → при создании машины отметьте секреты. Шлюз и переменные можно привязывать и к существующей машине (вкладка «Обзор»); подстановка задаётся только при создании. Ротация: измените значение — шлюз подхватывает сразу, подстановка — со следующего старта машины.

**Защита шлюза:** обслуживает только подключения с адресов самого хоста (машины, запущенные через CLI, приходят именно так; соседи по LAN — нет), токен 192 бит и привязан к паре «машина + секрет», токен в URL или в нескольких заголовках отклоняется, можно ограничить HTTP-методы. Порт — `SMOLVM_WEB_GATEWAY_PORT` (7790). Машины с секретами-шлюзом стартуют через CLI, т.к. под `smolvm serve` хост недоступен.

**Хранение:** `vault.enc.json` (AES-256-GCM); ключ шифрования — в Keychain (macOS), DPAPI (Windows), Secret Service/`secret-tool` (Linux), иначе в файле `vault.key` (0600). Для headless-сервера можно задать `SMOLVM_WEB_VAULT_KEY` (64 hex).

Ограничения:
- Защита от агента *внутри машины*. Процессы на хосте под вашим пользователем могут получить ключ (как и из любого менеджера паролей).
- Если API вернёт ключ в теле ответа, машина его увидит — это подстановка, а не DLP.
- Клиент, игнорирующий `NO_PROXY` (busybox `wget`), отправит запрос к шлюзу через корпоративный прокси — туда уйдёт токен машины, а не ключ. curl, Python, Node учитывают `NO_PROXY`.
- Машина с подстановкой smolvm стартует через API и не видит корпоративный прокси/шлюз — не смешивайте режимы на одной машине за прокси.

## Создание машины по Smolfile

«+ Машина» → профиль **«Из Smolfile»** → вставьте Smolfile или нажмите «Загрузить файл». Для относительных путей в `volumes` (`./src:/app`) укажите «Папку проекта».

```toml
image = "python:3.12-slim"
net = true
cpus = 2
memory = 2048
ports = ["8000:8000"]
volumes = ["./src:/app:ro"]
env = ["APP_ENV=dev"]
init = ["pip install fastapi uvicorn"]
cmd = ["sh", "-c", "while true; do sleep 3600; done"]

[network]
allow_hosts = ["pypi.org", "files.pythonhosted.org"]

[restart]
policy = "on-failure"
```

smolvm-web разбирает Smolfile так же строго, как smolvm (неизвестный ключ — ошибка с номером строки), и создаёт машину через HTTP API — поэтому она полноценная машина `smolvm serve`: консоль, файлы, логи, агенты, фильтр «Доступ в сеть» и секреты работают как обычно. (`smolvm machine create -s` поставил бы машину вне реестра работающего `smolvm serve`: `exec` и файлы не работали бы до его перезапуска.)

- **`init`** выполняется один раз при первом запуске, от root, после записи настроек прокси и сертификатов, с `env` из Smolfile. Вывод — в уведомлении «Показать вывод». Если команда упала, init повторится при следующем запуске.
- **Сверху можно добавить** то, чем управляет smolvm-web: корпоративный прокси, фильтр «Доступ в сеть», секреты.
- **Не переносятся** (HTTP API smolvm их не принимает): `[secrets]` и `[[network.credentials]]` — используйте «Секреты»; `allow_host_patterns` — используйте `allow_hosts` или фильтр «Доступ в сеть». Ключи только для CLI (`user`, `[health]`, `[service]`, `[dev]`, `[auth]`, `stop_on_exit`, `gpu_vram`…) пропускаются с предупреждением.
- Если `cmd`/`entrypoint` не заданы, машина держится командой `sleep`, чтобы workload образа не завершался сразу.

## Профили и ИИ-агенты

При создании машины выберите профиль — машина получит образ `node:22-bookworm-slim`, порты агентов и после первого запуска сама установит всё нужное (≈ 3 мин, прогресс — во вкладке «Агенты»):

| Профиль | Агенты |
|---|---|
| Claude Code | веб-терминал, Claude Code |
| OpenCode | веб-терминал, OpenCode (веб-интерфейс и TUI) |
| DeepSeek Harness | веб-терминал, `dsh web` |
| Все агенты | всё вышеперечисленное |

К существующей машине агентов можно подключить во вкладке «Агенты» (нужен Debian-образ с Node.js; машина перезапустится, чтобы опубликовать порты).

**Вкладка «Агенты»**: «Запустить» поднимает агента и открывает его в новой вкладке браузера (без запроса пароля), «Открыть» — для уже работающего; плюс «Задача без интерфейса» — `claude -p`, `opencode run`, `dsh headless` с потоковым выводом. Агенты работают в машине от пользователя `node` в `/work`.

**Модели.** Привяжите к машине секрет DeepSeek (или Anthropic/OpenAI) в режиме «Шлюз» — smolvm-web сам выставит переменные каждому агенту, ключ в машину не попадает:

| Агент | DeepSeek | Anthropic |
|---|---|---|
| Claude Code | `ANTHROPIC_BASE_URL=<шлюз>/anthropic`, `ANTHROPIC_AUTH_TOKEN`, модель `deepseek-flash` | `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` |
| OpenCode | провайдер `deepseek`, `baseURL={env:DEEPSEEK_BASE_URL}`, модель `deepseek/deepseek-flash` | провайдер `anthropic` |
| DeepSeek Harness | `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL=<шлюз>/anthropic` | — |

Модель можно сменить в самом агенте (`/model` в Claude Code, выбор модели в opencode, настройки dsh).

**Как это устроено.** Терминальные агенты (Claude Code, OpenCode TUI, bash) работают в [ttyd](https://github.com/tsl0922/ttyd) с паролем, OpenCode web — с `OPENCODE_SERVER_PASSWORD`, DeepSeek Harness — со своим одноразовым токеном (dsh слушает только loopback машины, поэтому рядом запускается ретранслятор). Порт машины публикуется на `127.0.0.1` хоста, а браузер ходит через прокси smolvm-web на соседнем порту (`<порт>+10000`): он подставляет пароль, пропускает WebSocket и отклоняет чужие `Host`/`Origin`. Напрямую опубликованный порт без пароля отвечает 401.

**За корпоративным прокси / с фильтром «Доступ в сеть»** установке нужны: `deb.debian.org`, `security.debian.org` (apt), `registry.npmjs.org` (npm), `github.com` и `*.githubusercontent.com` (ttyd), для OpenCode — `models.dev`. При создании машины с профилем и фильтром эти правила добавляются автоматически. Доступ к модели идёт через шлюз секретов на хосте, отдельно разрешать `api.deepseek.com` машине не нужно.

## Страховка для агентов

### Ревью изменений (вкладка «Изменения»)

Агент получает не саму папку хоста, а её **рабочую копию** внутри машины. Всё, что он меняет, остаётся в машине, пока вы не нажмёте **«Применить»** — целиком, по выбранным файлам или по одному после просмотра diff. **«Отклонить»** возвращает в машине версию файла с хоста.

- Копия делается упаковкой папки (tar) и загрузкой в машину, а не монтированием: смонтированные папки не дают делать снимки, а staged-монтирования smolvm сами копируют изменения на хост при остановке машины — без ревью.
- Изменения считаются по SHA-256 относительно манифеста на момент копирования. **Конфликт** — файл изменился и в машине, и на хосте; применение перезапишет хост, поэтому спрашивается подтверждение.
- «Подтянуть с хоста» обновляет в машине файлы, которые агент не трогал, а на хосте они изменились.
- Исключения по умолчанию: `.git`, `node_modules`, `.venv`, `__pycache__`, `dist`, `target` и т.п.
- Запись на хост атомарная, только внутри выбранной папки; symlink-компоненты пути и `..` отклоняются; символические ссылки не применяются автоматически.

### Снимки и откат (вкладка «Снимки»)

Снимок — `smolvm machine checkpoint`: память, процессы и диски, пауза машины — доли секунды. **«Откатить»** пересоздаёт машину из снимка под тем же именем через API smolvm; агенты, секреты, «Доступ в сеть» и состояние рабочих копий сохраняются. Перед откатом текущее состояние сохраняется **страховочным снимком**, и если восстановленная машина не запустится, она возвращается из него.

- Во вкладке «Агенты» включите **«Снимок перед запуском»** — снимок перед каждым запуском агента и задачей.
- Машины с агентами и машины, где включены снимки, запускаются с ветвлением (`--branchable`, на macOS обязательно для снимков).
- smolvm не снимает машины с подключёнными папками хоста, GPU/CUDA — используйте рабочие копии вместо монтирования.
- Новые машины smolvm-web создаёт с явным `networkBackend: virtio-net`: у машин со «неявным» сетевым режимом без портов smolvm восстанавливает снимок с другим сетевым устройством, и откат не запускается — для таких машин вкладка объясняет это заранее.
- Хранится последних 10 снимков на машину; файлы — в каталоге настроек (`checkpoints/`).

### Режим обучения для allow list

Страница «Доступ в сеть», колонка **«Обучение»**: фильтр временно разрешает всё и запоминает, куда ходила машина (адреса хоста и внутренней сети по-прежнему только по явному правилу). Кнопка **«Собрать»** показывает собранные хосты — снимите лишние, при желании замените хост на `.домен`, и одной кнопкой они станут списком, подключённым к машине; обучение выключится.

### Аудит (страница «Аудит»)

- **Журнал действий**: команды exec (консоль, задачи агентам, init) с кодом выхода, запуски/остановки/удаления машин, загрузки файлов, применение и отклонение в ревью (какие файлы), снимки и откаты, изменения секретов (без значений), правил сети, директорий и настроек. Кто — `ui@<адрес>`, `smolvm-web` для автоматических действий, `… → агент` для задач.
- **Изменения файлов** в папках хоста, подключённых к работающим машинам на запись (`fs.watch`). Источник — машина или человек на хосте — по файловой системе не различить; в записи перечислены машины с доступом на запись.
- Команды, которые агент выполняет внутри машины сам, smolvm не сообщает — их след: сетевой журнал и изменения файлов.
- Хранение: `audit.log` (JSON lines, ротация 10 МБ), экспорт в JSONL с кнопки.
- **SIEM**: syslog RFC 5424 (UDP/TCP, сообщение — JSON, facility local0–7) и/или HTTP POST пачек JSON (Splunk HEC, Elastic, Graylog и т.п., заголовок Authorization хранится только на сервере). Сетевые события фильтра — по выбору: только блокировки или все.
- **Оповещения**: N заблокированных соединений одной машины за M секунд → уведомление в интерфейсе, запись в журнал, SIEM и веб-хук (POST JSON с полем `text`).

## Изоляция ИИ-агентов

### Доступ в сеть: allow list (egress-фильтр)

Страница **Доступ в сеть** (`#/egress`). На хосте работает фильтрующий HTTP(S)-прокси smolvm-web (порт `SMOLVM_WEB_EGRESS_PORT`, по умолчанию 7791). Машине с включённым фильтром в `HTTP(S)_PROXY` подставляется адрес этого прокси с её собственным токеном; каждое соединение сверяется с allow list машины и уходит в интернет хоста — через корпоративный прокси, если он настроен, иначе напрямую.

| Что | Как |
|---|---|
| Правила | `api.example.com` — ровно хост; `.example.com` — хост и поддомены; `*.example.com` — только поддомены; `10.0.0.0/8`, `192.0.2.10` — IP; `*` — любой. Порты: `443` (по умолчанию), `443,80`, `8000-8100`, `*`. Можно вставить URL — хост и порт извлекутся. |
| Списки | Именованные наборы правил («Общий», «LLM API», …) с шаблонами: PyPI, npm, GitHub, Docker Hub, apt/apk, Go, crates.io, Hugging Face, OpenAI, Anthropic, DeepSeek, OpenRouter, Gemini. Машина подключает списки и может иметь собственные правила. Отмеченные «подключать к новым машинам» включаются автоматически. |
| Журнал (отдельная страница) | Все соединения (разрешено/заблокировано, правило, трафик, путь — через корп. прокси или напрямую). Заблокированные собираются в блок «Разрешить»: хост или домен целиком добавляется в список или в правила машины одной кнопкой. Файл: `egress.log` в каталоге настроек. |
| Применение | Правила — сразу, без перезапуска. Включение фильтра для существующей машины — сразу для консоли/exec и профиля гостя (profile.d, pip, npm, apt, git), для основного процесса машины — при следующем запуске через smolvm-web (`smolvm machine update --env`). |
| Защита хоста | Адреса хоста, loopback, link-local (169.254.x — metadata), частные сети доступны только по явному правилу IP/CIDR — даже если разрешённое имя на них резолвится; `*` их не открывает. Без токена — 407, с чужих адресов (LAN) — 403. |
| Жёсткая изоляция | Фильтр видят только программы, учитывающие `HTTP(S)_PROXY`. С флажком «Жёстко» smolvm получает egress-политику «только IP хоста» (`allowedCidrs`), так что в обход фильтра наружу не выйти. Применяется при создании или при старте остановленной машины через smolvm-web. Учтите: машине доступны и другие сервисы хоста на внешнем интерфейсе. |
| Образы | Образ при старте качается отдельным токеном, которому дополнительно разрешены реестры (список — в настройках страницы). |

Ограничения: HTTPS не расшифровывается — фильтр работает по хосту и порту, не по пути. Машины с подстановкой smolvm (`substitute`) стартуют через API и до фильтра не достают. Если IP хоста сменился, жёсткая политика обновится при следующем запуске.

### Директории и права пользователей

Страница **Директории** (`#/dirs`).

1. **Разрешённые директории хоста** — реестр: имя, путь на хосте, путь в машине, «максимум» (только чтение / чтение и запись) и доступ по умолчанию. Нельзя добавить корень диска, домашнюю директорию целиком, системные пути и места с ключами (`~/.ssh`, `~/.aws`, `~/.kube`, `~/.docker`, настройки smolvm-web…). Каталог настроек smolvm-web (там хранилище секретов) не монтируется никогда, в том числе через поле «Монтирования». **Строгий режим** разрешает в поле «Монтирования» формы создания только директории из реестра в пределах их максимума.
2. **Доступ в машине** — пользователи гостя (создаются автоматически, можно задать uid) и матрица «директория × пользователь»: запись / чтение / нет доступа, плюс «остальные» для всех неперечисленных. Кнопка «Проверить фактические права» выполняет в машине проверку от имени каждого пользователя.

Как обеспечивается:

- **Хост**: каждая директория монтируется в машину до двух раз — представление на запись (если кому-то нужна запись) и read-only представление (если кому-то нужно только чтение). Read-only обеспечивает хост: при «максимуме» «только чтение» не пишет даже root в машине.
- **Гость**: представления лежат в `/.smolvm-dirs/<имя>/{rw,ro}/data` за «шлюзами» — каталогами 0700 с POSIX ACL для нужных пользователей (пакет `acl` ставится в машину автоматически; без него — один пользователь на представление). smolvm exec сбрасывает дополнительные группы, поэтому группы не используются. Путь в машине (`/work`) — ссылка на самое широкое представление; у каждого пользователя есть `~/work` на своё; при наличии записи read-only представление ещё и в `/work-ro`.
- Смена прав внутри уже смонтированных представлений применяется сразу. Новая директория или новое представление требуют перезапуска (кнопка «Перезапустить сейчас»): smolvm меняет монтирования только у остановленной машины, smolvm-web делает это `smolvm machine update --volume` прямо перед стартом.

Ограничения: **root в машине обходит права гостя** — запускайте агентов от обычных пользователей (поле «user» в консоли, `"user"` в API exec). Монтирование сохраняет владельца с хоста: писать может пользователь с uid владельца директории на хосте (UI подсказывает uid). При самом первом запуске шлюзы закрываются сразу после старта, а не до него.

## Безопасность

`smolvm serve` **не имеет аутентификации**: доступ к API = shell на хосте. Поэтому прокси:

- слушает только `127.0.0.1`;
- отклоняет запросы с чужим `Host` (DNS rebinding) и `Origin`;
- требует заголовок `X-Smolvm-UI: 1` для изменяющих запросов.

Настройки (могут содержать пароль прокси) хранятся с правами `0600`. Не публикуйте порт наружу.

Файлы в каталоге настроек: `settings.json`, `state.json`, `vault.enc.json` (секреты), `egress.json` (allow list и токены машин), `dirs.json` (директории и права), `egress.log` (журнал соединений), `audit.json` / `audit.log` (аудит), `review.json` (рабочие копии), `snapshots.json` + `checkpoints/` (снимки), `agents.json`, `smolfile.json`.

## Замечания

- Остановка `smolvm serve` **не останавливает машины**.
- Консоль не интерактивная (нет TTY): для полноценного shell — `smolvm machine exec -it --name <имя> -- sh`.
