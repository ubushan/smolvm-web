## Первые шаги

Типовая настройка изолированного агента:

1. **Сеть** (если вы за корпоративным прокси): «Настройки» (шестерёнка в шапке) → «Прокси» → «Определить автоматически» → «Проверить» → при TLS-инспекции включите «Доверять корпоративным сертификатам» → «Сохранить». См. [Корпоративный прокси](#корпоративный-прокси).
2. **Ключ модели**: «Настройки» → «Секреты» → «Добавить секрет» → шаблон (DeepSeek, Anthropic, OpenAI…) → режим «Шлюз smolvm-web». Ключ не попадает в машину. См. [Секреты и API-ключи](#секреты-и-api-ключи).
3. **Allow list**: страница «Сеть» → создайте или дополните список разрешённых ресурсов (есть шаблоны PyPI, npm, GitHub и др.). Для первичной настройки удобен [режим обучения](#режим-обучения-для-allow-list). См. [Сеть](#сеть-allow-list-egress-фильтр).
4. **Папки**: «Дать доступ к папке» (страница «Директории», блок «Папки агента» в «Обзоре», окно создания машины) → папка, машина, режим: только чтение, рабочая копия с ревью или чтение и запись. Для кода лучше рабочая копия. См. [Папки компьютера для агентов](#директории-и-права-пользователей).
5. **Машина**: «Создать» → профиль агента (Claude Code, OpenCode, DeepSeek Harness) или «Из Smolfile» → отметьте секреты, фильтр «Сеть», при необходимости жёсткую изоляцию и директории → «Создать». Агенты установятся при первом запуске. См. [Профили и ИИ-агенты](#профили-и-ии-агенты).
6. **Работа**: вкладка «Агенты» → «Запустить» (агент откроется в новой вкладке).
7. **Контроль**: «Сеть» → вкладка «Журнал» — куда ходят машины и что заблокировано; «Аудит» — команды и изменения файлов (экспорт в SIEM и оповещения — «Настройки» → «Аудит и SIEM»); страница «Директории» → «Изменения агента» — что агент сделал с рабочей копией.

## Интерфейс

| Раздел | Что там |
|---|---|
| **Рабочие места** (стартовая страница, `#/work`) | Карточки рабочих мест: агент, шаблон машины и что лежит в профиле (MCP-серверы, skills, инструкции, память), режим сети. «Открыть» — чистая песочница с этим агентом и профилем; у открытой — «Перейти к агенту» и «Закрыть» (изменения профиля уходят на ревью). Сверху — напоминание, если изменения профиля ждут проверки; ниже — разовые песочницы без профиля. Кнопки: «Новое место» (название, агент, шаблон, настройки — пустые или из запущенной машины), «Разовая песочница» (окно «Новая песочница»: агент, профиль, «Открыть»). Шестерёнка на карточке открывает файлы профиля. |
| **Сеанс** (`#/session?name=…`) | Экран открытой песочницы: слева все открытые песочницы, сверху режим сети, «Изолировать», «Сохранить и закрыть» (или «Без сохранения»); в центре агент («Открыть агента», другие агенты, «Дать папку», ссылка на машину) и что происходило по журналу аудита; справа — что загружено из профиля, «Изменится при закрытии» (кнопка «Проверить сейчас» показывает, что заберётся в профиль, ничего не сохраняя) и сеть за сеанс. Открывается после запуска песочницы и по «Перейти к агенту». |
| **Профиль агента** (`#/profile?id=…`, шестерёнка на карточке рабочего места) | Разделы: инструкции, MCP и настройки, skills, подагенты и команды, память, хуки и плагины — с числом файлов; список файлов раздела и редактор. «Новый файл», удаление, «Проверять изменения перед сохранением» (выключение = «без ревью»), «Открыть песочницу». Если в MCP-конфиге или настройках агента токен записан открытым текстом, показывается предупреждение (имя ключа, без значения) со ссылкой на «Секреты»: такой токен попадает в каждую песочницу и виден агенту. |
| **Проверка изменений** (`#/review`) | Что агент хочет сохранить в профиль после закрытия песочницы: карточка на каждое изменение (skill, память, инструкции, MCP), diff справа. Skills, хуки, MCP и настройки заранее не отмечены и выделены как исполняемые настройки. «Сохранить выбранное» записывает отмеченное и отклоняет остальное, «Отклонить всё» оставляет профиль как был. Подозрительные добавленные строки подсвечиваются красным с причиной: ключи SSH и файлы с учётными данными, «скачать и выполнить», отправка данных наружу (scp, rsync, nc, curl -d), переменные с ключами, скрытое выполнение (base64 -d, eval), обход проверок, фразы prompt injection. |
| **Машины** (`#/`) | Список машин и карточка выбранной. Вкладки: «Обзор» (параметры и блоки: порты, сеть, папки агента, секреты, образы, прокси), «Агенты», «Консоль», «Детали» (полный ответ smolvm о машине), «Логи», «Файлы». Внизу списка машин — нагрузка CPU, память, диск, сколько машин запущено и uptime smolvm serve. Ревью рабочих копий — на странице «Директории», блокировки egress-политики smolvm и провайдеры агентов — на странице «Сеть». Если «смертельная триада» разорвана, вверху «Обзора» одна зелёная строка «Риск утечки низкий» с причиной (подробности по нажатию); если нет — красное предупреждение и блок «Риск утечки» с кнопкой «Разорвать». Состояния машин — по-русски: работает, остановлена, на паузе. Кнопки: старт / branchable-старт, перезапуск (через smolvm-web: подключаются новые папки, применяются фильтр, прокси и uid агента), пауза, ветка, стоп, удаление, «Применить прокси». |
| **Сеть** | Сверху — «Ждут ответа»: запросы машин с включённым «Спрашивать о незнакомых адресах» («На 10 минут», «Всегда», «Запретить», с таймером). Вкладки: «Машины» — карточка каждой машины: режим («Без ограничений» / «Только разрешённое» / «Запись адресов»), что разрешено (списки, свои правила, серверы агентов), недавно заблокированное с кнопкой «Разрешить», «Проверить адрес»; «Журнал» — фильтры «Все / Заблокированные / Разрешённые», машина, поиск, пауза обновления; блок «Ждут решения» с кнопкой «Разрешить» (для машины, шире или в список); лента соединений; свёрнутый блок «Заблокировано самой smolvm»; «Списки» — наборы разрешённых адресов карточками и раздел «Только для скачивания образа» со служебным списком «Реестры образов» (откуда smolvm скачивает образ машины при запуске; агенту эти адреса закрыты); «Настройки» — режим и списки для новых машин, состояние фильтра (работает ли, выход в интернет, адрес компьютера для машин). |
| **Аудит** | В шапке — «Журнал цел» (цепочка подписей проверяется при открытии страницы; нажатие — проверить снова) и состояние экспорта в SIEM (нажатие открывает настройки). Счётчики за сутки (команды, действия с машинами, настройки, файлы, оповещения, ошибки — нажатие фильтрует), фильтры по типу, машине и тексту, лента событий по дням, экспорт JSONL. SIEM и оповещения — «Настройки» → «Аудит и SIEM». |
| **Песочницы** (`#/sandbox`, ссылки внизу «Рабочих мест») | Вкладки: «Песочницы» — панель запуска (шаблон, профиль, агент) и карточки открытых песочниц с кнопками агентов, «Папка», «Закрыть»; «Ревью» — изменения профиля: список файлов слева, diff справа; «Профили» — карточки профилей, файлы открываются со встроенным редактором; «Шаблоны» — карточки шаблонов, «Обновить», новый шаблон из машины с агентами. |
| **Директории** | Кнопка «Дать доступ к папке» и вкладки: «Папки машин» (режим и статус каждой папки: «✓ работает», «нужен перезапуск», почему не работает), «Изменения агента» (ревью рабочих копий), «Разрешённые папки» (политика, строгий режим). |
| **Настройки** (шестерёнка в шапке; на узком экране — без подписи) | Окно с разделами слева: «Виртуализация» (установленная версия smolvm, состояние `smolvm serve`, гипервизор, путь к бинарнику), «Прокси», «Сертификаты», «Репозитории», «Секреты» (хранилище API-ключей), «Аудит и SIEM» (экспорт журнала в SIEM, оповещения о всплесках блокировок). «Песочницы» — политика по умолчанию для новых песочниц: срок жизни (часов; потом закрывается сама, изменения профиля — на проверку; открытую можно продлить кнопкой «+2 ч» на экране сеанса), закрытие при простое (минут без запросов в сеть и к API моделей), «Спрашивать о незнакомых адресах», лимиты процессов, времени агента и запросов API. По умолчанию всё выключено; уже открытые песочницы не меняются. Окно открывается на последнем выбранном разделе. |
| **Подвал страницы** | Версия и коммит запущенного smolvm-web (если smolvm-web скачан архивом, без папки `.git`, коммит неизвестен — так и написано). Если код на диске обновлён (`git pull`), а сервер ещё работает на старом, там появится напоминание перезапустить smolvm-web. |
| **«?»** в разделах | Встроенная справка по разделу. |

## Параметры запуска

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SMOLVM_API` | macOS/Linux: `unix:///tmp/smolvm.sock`<br>Windows: `http://127.0.0.1:18899` | адрес `smolvm serve` |
| `SMOLVM_BIN` | `smolvm` | путь к бинарнику (`C:\tools\smolvm.exe`); настройка «Путь к бинарнику smolvm» в интерфейсе важнее |
| `PORT` | `7777` | порт веб-интерфейса |
| `SMOLVM_AUTOSTART` | — | `1` = то же, что `--autostart` |
| `SMOLVM_WEB_EGRESS_PORT` | `7791` | порт egress-фильтра (allow list) на хосте |
| `SMOLVM_WEB_HOME` | `~/.config/smolvm-web`, Windows: `%APPDATA%\smolvm-web` | настройки и лог `smolvm-serve.log` |
| `SMOLVM_WEB_GATEWAY_PORT` | `7790` | порт шлюза секретов на хосте |
| `SMOLVM_WEB_RELAY_PORT` | `7792` | порт ретранслятора для «Системного прокси Windows» |
| `SMOLVM_WEB_VAULT_KEY` | — | ключ хранилища секретов (64 hex) для headless-сервера без хранилища ключей ОС |

Пример: `PORT=7800 SMOLVM_BIN=/opt/smolvm/smolvm ./start.sh` (Windows: `set PORT=7800 && start.cmd`).

**Путь к smolvm в интерфейсе.** Кнопка **«Настройки»** (шестерёнка в шапке) → раздел **«Виртуализация»** → «Путь к бинарнику smolvm» (например `C:\smolvm\smolvm.exe` или `/opt/smolvm/smolvm`), «Проверить» запускает `<путь> --version`. Путь сохраняется в настройках и применяется сразу ко всем вызовам CLI; `smolvm serve`, запущенный `--autostart`, использует его при следующем запуске smolvm-web. Пустое поле — `SMOLVM_BIN` или `smolvm` из `PATH`.

### Особенности Windows

- smolvm на Windows не поддерживает Unix-сокет, поэтому API слушает loopback TCP `127.0.0.1:18899`. Нужна включённая Windows Hypervisor Platform.
- Вывод `smolvm serve` и `smolvm machine start` пишется в файл, а не в pipe: на Windows CLI иначе не возвращает управление.
- Пути с буквой диска принимаются и в «Дать доступ к папке», и в поле «Тома smolvm»: `C:\Users\me\project`, `D:/data:/data:ro`.
- «Определить автоматически» берёт системный прокси из `Internet Settings` (реестр), сертификаты — из хранилища Windows.

- **Без прав администратора.** Права администратора нужны только для двух вещей: включить Windows Hypervisor Platform (один раз, с перезагрузкой) и — при первом запуске smolvm (и после его обновления) — распаковать агентский rootfs с символическими ссылками. Сам smolvm прав администратора не проверяет, smolvm-web тоже; Kerberos/NTLM-вход в прокси от обычного пользователя работает естественно (это его учётная запись). Право на symlink без администратора на каждый день — любой из вариантов:
  1. «Режим разработчика» (Параметры → Система → Для разработчиков) — на управляемых компьютерах его часто включает только ИТ;
  2. администратор выдаёт вашей учётной записи право «Создание символических ссылок» (`secpol.msc` → Локальные политики → Назначение прав пользователя → Создание символических ссылок; затем выйти и войти);
  3. один раз запустить smolvm от администратора **под той же учётной записью** (распаковка ляжет в ваш `%LOCALAPPDATA%`): `smolvm machine run --net --image alpine -- true` в PowerShell «от имени администратора». Дальше smolvm-web и smolvm работают от обычного пользователя, пока обновление smolvm не потребует новой распаковки — тогда повторить.
  
  Авторы smolvm проверяли его на Windows только в сессии администратора, так что запуск от обычного пользователя — проверенный нами лишь по коду путь: если что-то не заработает, пришлите ошибку.
- **Право на символические ссылки при распаковке обязательно.** smolvm распаковывает свой агентский rootfs из tar в `%LOCALAPPDATA%\smolvm\rootfs\` и без права на symlink теряет `/sbin/init`: машины падают с `boot process exited (code 127)` / `Couldn't execute '/sbin/init': ENOENT`. smolvm-web проверяет это при запуске и в интерфейсе: показывает баннер и кнопку **«Починить»**, которая удаляет испорченную распаковку (только каталоги rootfs без `/sbin/init`), чтобы smolvm распаковал её заново. Перед починкой право на symlink должно уже быть.

Подробное развёртывание, автозапуск и частые проблемы — в [INSTALL.md](INSTALL.md).

## Корпоративный прокси

Кнопка **«Настройки»** (шестерёнка в шапке, или индикатор прокси) → раздел **«Прокси»** (сертификаты — раздел **«Сертификаты»**).

По умолчанию прокси выключен: машины и smolvm ходят в интернет напрямую. Пока он выключен, переменные `HTTP(S)_PROXY`/`NO_PROXY` из окружения Windows или shell в smolvm не передаются. Настройки хранятся в каталоге настроек (`%APPDATA%\smolvm-web`, `~/.config/smolvm-web`) и переживают переустановку smolvm-web; чтобы начать с чистых настроек, удалите там `settings.json`.

| Что | Как реализовано |
|---|---|
| Запуск и образы | При включённом прокси машина стартует через `smolvm machine start [--proxy … --no-proxy …]`: HTTP API smolvm при старте тянет образ без прокси, а `smolvm serve` ставит строгую egress-политику (`SMOLVM_EGRESS_FLOOR=strict`), при которой машины не видят хост и LAN — то есть и корпоративный прокси. Pull во вкладке «Образы» получает поле `proxy`. |
| Переменные в машине | `HTTP(S)_PROXY`, `NO_PROXY` (в обоих регистрах) добавляются в `env` при создании и в каждый `exec` из консоли/API. Явно заданные переменные не перезаписываются. |
| Настройка гостя после старта | `/etc/profile.d/smolvm-proxy.sh`, `/etc/pip.conf`, глобальный `npmrc`, `/etc/apt/apt.conf.d/95smolvm-proxy`, `git config --system http.proxy`. Для уже запущенной машины — кнопка «Применить прокси». |
| Прокси на `localhost` хоста (cntlm, px) | Внутри машины `localhost` — это сама машина, поэтому адрес переписывается на IP хоста. Прокси должен слушать этот интерфейс (`Gateway yes` в cntlm, `--gateway` в px). |
| TLS-инспекция | Bundle = публичные корневые (Mozilla) + сертификаты ОС + ваш PEM/файл. Кладётся в `/etc/smolvm-host-trust/ca-bundle.pem`, на него указывают `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `GIT_SSL_CAINFO` и др.; опционально заменяет системный bundle гостя (apk, apt, curl, wget). |
| Скачивание образа за TLS-инспекцией | Образ при старте качает `crane` внутри гостевого агента smolvm, до записи настроек в машину. С галочкой «Доверять им при скачивании образа» (по умолчанию включена) smolvm-web пишет тот же bundle в `<каталог настроек>/host-trust/ca-bundle.pem` и подключает его к машине read-only томом `/etc/smolvm-host-trust` — так же, как `--trust-host-certs` smolvm, который сам не умеет читать хранилище Windows. Том добавляется при создании, а у существующих машин — при следующем запуске через smolvm-web (`machine update --volume`). Ошибка `x509: certificate signed by unknown authority` при запуске показывается с подсказкой, что включить. Цена: smolvm не делает снимки машин с томами хоста — когда образ уже скачан, галочку можно выключить, и том отключится при следующем запуске. |
| Проверка | «Проверить» делает `CONNECT` к docker.io / pypi.org / npmjs.org через прокси с хоста и по адресу, который увидят машины. |
| Исключения | NO_PROXY общий; на отдельной машине прокси можно выключить (вкладка «Обзор» или чекбокс при создании). |

Если `smolvm serve` запускается через `--autostart` при включённом прокси, ему тоже передаются `HTTPS_PROXY`/`NO_PROXY` (запросы к реестрам со стороны хоста). После изменения прокси перезапустите smolvm-web, чтобы это применилось.

Альтернатива для образов — корпоративный реестр, см. [Корпоративные репозитории](#корпоративные-репозитории).

### Системный прокси Windows (PAC, Kerberos / NTLM)

Галочка **«Системный прокси Windows»** (только на Windows; «Определить автоматически» включает её сама, если в Windows задан прокси или PAC-файл) — smolvm-web работает с прокси как браузер:

- **Адрес** берётся из настроек Windows (Internet Settings): PAC-файл (`AutoConfigURL`) вычисляется для каждого адреса назначения (`FindProxyForURL`, `DIRECT` — напрямую), либо `ProxyServer` с исключениями `ProxyOverride`. Настройки перечитываются раз в минуту, PAC — раз в 10 минут.
- **Вход** — под вашей учётной записью Windows, без пароля: на ответ `407` с `Negotiate` (Kerberos, с откатом на NTLM) или `NTLM` smolvm-web получает токен через SSPI (`InitializeSecurityContext`) — небольшой помощник на PowerShell, который smolvm-web запускает сам (`<каталог настроек>\sspi-helper.ps1`). Логин и пароль в адресе прокси по-прежнему работают (Basic).
- **Машины** не умеют входить под вашей учётной записью, поэтому получают в `HTTP(S)_PROXY` **ретранслятор** smolvm-web на этом компьютере (порт 7792, с токеном): он выбирает прокси по PAC и входит в него за машину — как px или proxydetox, только встроенный. Через него же идут скачивание образов (`--proxy`), `smolvm serve`, egress-фильтр, шлюз секретов и загрузки smolvm-web (ttyd). Сервисы самого компьютера через ретранслятор недоступны.
- «Проверить» показывает для каждого адреса, какой прокси выбран и как прошёл вход (Kerberos/Negotiate, NTLM, Basic), и проверяет ретранслятор (после сохранения настроек).

Ограничения: обычный HTTP (не HTTPS) через прокси, требующий NTLM, не поддерживается (Kerberos — да); WPAD-автообнаружение без явного PAC-адреса не поддерживается; если PowerShell запрещает `Add-Type` (режим ограниченного языка, AppLocker), встроенный вход недоступен — тогда px/proxydetox. На macOS/Linux — адрес прокси вручную, для Kerberos/NTLM — локальный cntlm/px.

Логин/пароль в URL прокси (ручной режим) видны процессам внутри машины.

## Корпоративные репозитории

Кнопка **«Настройки»** (шестерёнка в шапке) → раздел **«Репозитории»**. Подходит для JFrog Artifactory, Sonatype Nexus, Harbor и любых других прокси-репозиториев. Все поля необязательны: заполните только то, что есть.

| Поле | Пример (Artifactory) | Что делает |
|---|---|---|
| Реестр образов | `artifactory.corp.local/docker-remote` | с галочкой «Брать образы Docker Hub из этого реестра» образы Docker Hub при создании машины переписываются: `node:22` → `artifactory.corp.local/docker-remote/library/node:22`, `docker.io/bitnami/redis` → `…/bitnami/redis`. Образы других реестров (`ghcr.io/…`) не меняются. Профили агентов тоже идут через реестр. |
| Пользователь / токен | `ci-bot` / API key или Identity token | логин к реестру образов: smolvm-web пишет `<каталог настроек>/docker/config.json` (ваш `~/.docker/config.json` + запись `auths`) и передаёт его smolvm через `DOCKER_CONFIG`, как после `docker login`. В машину логин не попадает. Токен хранится в `settings.json` (0600) и не отдаётся браузеру. |
| PyPI | `https://artifactory.corp.local/api/pypi/pypi-remote/simple` | `PIP_INDEX_URL` в консоли/exec и `index-url` в `/etc/pip.conf` (для `http://` — ещё `trusted-host`) |
| npm | `https://artifactory.corp.local/api/npm/npm-remote` | `NPM_CONFIG_REGISTRY` и `registry=` в глобальном `npmrc` (установка агентов тоже идёт через него) |
| apt: вместо deb.debian.org/debian и …/debian-security | `https://artifactory.corp.local/artifactory/debian-remote` | заменяет адреса в `/etc/apt/sources.list` и `/etc/apt/sources.list.d/debian.sources` (оригиналы — `*.smolvm-orig`) |
| Go | `https://artifactory.corp.local/artifactory/api/go/go-remote` | `GOPROXY` (+ `GONOSUMDB=*`), `/etc/profile.d/smolvm-go.sh` |
| GitHub releases | `https://artifactory.corp.local/artifactory/github-remote` (generic remote на `https://github.com`) | откуда качать бинарники с GitHub при установке агентов вместо `https://github.com`. Веб-терминал ttyd smolvm-web скачивает сам на этом компьютере (через корпоративный прокси, если он включён, или с этого зеркала) и загружает в машину, так что машине GitHub не нужен |

**Уже созданные машины.** Образ машины фиксируется при создании, а smolvm не умеет менять его у существующей машины. Машина, созданная до настройки реестра, продолжит качать образ с Docker Hub; без прямого доступа запуск упадёт (`crane manifest failed … index.docker.io … TLS handshake timeout`) — smolvm-web покажет, какой образ из реестра будет использован, и предложит создать машину заново. Машина, которая ни разу не запускалась, пуста — её можно просто удалить. (Встроенный в smolvm `mirror` для `docker.io` в `~/.config/smolvm/config.toml` не помогает: образ скачивается под именем зеркала и потом не находится.)

**ttyd без доступа к GitHub.** Веб-терминал — это бинарник ttyd с GitHub (в Debian bookworm пакета нет). При установке агентов smolvm-web берёт его так: файл `ttyd.x86_64` / `ttyd.aarch64` из папки `<каталог настроек>/bin` (например `%APPDATA%\smolvm-web\bin`), иначе скачивает на этом компьютере — с зеркала GitHub releases или с github.com (через корпоративный прокси, если он включён в настройках; для конкретной машины прокси при этом можно выключить) — и загружает в машину. Если у компьютера нет доступа ни туда, ни туда, скачайте `https://github.com/tsl0922/ttyd/releases/download/1.7.7/ttyd.x86_64` где получится, положите в эту папку и повторите установку.

**Логин внутри машины.** По умолчанию пакетные репозитории читаются анонимно. Если им нужен логин, включите «Передавать пользователя и токен в машину»: тогда он добавляется в URL pip и Go, в `npmrc` (`_auth`) и в `/etc/apt/auth.conf.d/smolvm.conf`. Агент в машине сможет прочитать этот токен — выдайте для этого отдельную учётную запись только на чтение.

**Сеть.** Хосты репозиториев автоматически разрешены фильтру «Сеть» (все порты, источник «корпоративные репозитории»), в том числе когда они резолвятся во внутренние адреса; адреса самого хоста и `127.0.0.0/8` по-прежнему закрыты.

**Сертификаты репозиториев.** Если хоть один пакетный репозиторий указан по `https://`, smolvm-web передаёт в машину CA bundle — публичные корни + сертификаты, которым доверяет этот компьютер (внутренний CA, которому доверяет браузер, там уже есть) + PEM из раздела сертификатов — даже при выключенных «корпоративных сертификатах». apt получает `Acquire::https::CaInfo` (`/etc/apt/apt.conf.d/95smolvm-ca`), а в slim-образах без пакета `ca-certificates` создаётся `/etc/ssl/certs/ca-certificates.crt` — иначе apt пишет `No system certificates available. Try installing ca-certificates`. Если CA репозитория нет в хранилище ОС (или Node.js старше 22.15 и не читает его), вставьте его PEM в «Настройки» → «Сертификаты».

При включённом корпоративном прокси запросы к репозиторию идут через него; если репозиторий во внутренней сети и прокси его не пропускает, добавьте его хост в NO_PROXY — тогда и фильтр, и машина пойдут к нему напрямую. За TLS-инспекцией или с внутренним CA репозитория включите корпоративные сертификаты (раздел выше).

Настройки гостя (pip, npm, apt, Go) применяются при запуске машины через smolvm-web и кнопкой «Применить прокси»; переменные консоли и exec — сразу. `smolvm serve`, запущенный через `--autostart`, видит логин к реестру сразу после сохранения; если вы запускаете `smolvm serve` сами, задайте ему `DOCKER_CONFIG=<каталог настроек>/docker`.

## Секреты и API-ключи

Ключ (DeepSeek, OpenAI, GitHub…) хранится в зашифрованном хранилище на хосте, а агент в машине может им **пользоваться, но не может его прочитать**. Значение не попадает ни в машину, ни в её запись в smolvm, ни в интерфейс (после сохранения оно не показывается).

| Режим | Что видит машина | Как работает | Когда |
|---|---|---|---|
| **Шлюз smolvm-web** | `DEEPSEEK_API_KEY=smolgw_…` (токен машины), `DEEPSEEK_BASE_URL=http://<IP хоста>:7790/g/deepseek` | SDK шлёт запрос на шлюз; шлюз проверяет токен, меняет его на ключ и отправляет на `https://api.deepseek.com` — **через корпоративный прокси**, если он настроен | По умолчанию за прокси |
| **Подстановка smolvm** | `DEEPSEEK_API_KEY=SMOL_PLACEHOLDER_…` | Родной [credential substitution](https://github.com/smol-machines/smolvm/blob/main/docs/credential-substitution.md): хост подменяет заглушку в HTTPS-заголовке, только к указанным хостам. Значения передаются в `smolvm serve` (`PUT /credential-values`) перед каждым стартом | Есть прямой интернет. Перехватчик smolvm ходит к API **без прокси** — за корпоративным прокси не работает |
| **Переменная** | значение как есть | Добавляется в команды консоли/exec | Только то, что программа должна прочитать сама (URL БД) |

Пример для агента (OpenAI-совместимый SDK, DeepSeek):

```python
from openai import OpenAI
import os
client = OpenAI(base_url=os.environ["DEEPSEEK_BASE_URL"], api_key=os.environ["DEEPSEEK_API_KEY"])
```

Как пользоваться: «Настройки» → «Секреты» → «Добавить секрет» (есть шаблоны DeepSeek/OpenAI/Anthropic/OpenRouter/Gemini/GitHub) → при создании машины отметьте секреты. Шлюз и переменные можно привязывать и к существующей машине (вкладка «Обзор»); подстановка задаётся только при создании. Ротация: измените значение — шлюз подхватывает сразу, подстановка — со следующего старта машины.

**Локальная модель (Ollama, vLLM, LM Studio, llama.cpp, свой DeepSeek).** «Настройки» → «Секреты» → «Добавить секрет» → шаблон «Локальная модель (OpenAI-совместимая)»: режим «Шлюз», URL API — адрес OpenAI-совместимого сервера (`http://localhost:11434/v1` для Ollama, `http://localhost:8000/v1` для vLLM, `http://<сервер>:<порт>/v1` для машины в сети), галочка «Локальная модель / сервер по HTTP», значение — ключ сервера (если сервер без ключа — любая строка). Шлюз работает на хосте, поэтому `localhost` в URL — это сам хост: серверу модели не нужно слушать сетевой интерфейс. Машина получает `LOCAL_LLM_API_KEY` (токен) и `LOCAL_LLM_BASE_URL` (адрес шлюза); к HTTP-адресам шлюз ходит напрямую, без корпоративного прокси. Укажите поле «Модель» (имя модели на сервере, например `deepseek-r1:14b` для Ollama или `deepseek-ai/DeepSeek-R1-Distill-Qwen-14B` для vLLM) — тогда OpenCode, Pi и Hermes настроятся на неё сами (см. [Модели и ключи](#модели-и-ключи)). Нейтральные имена переменных выбраны специально: автонастройка под облачные DeepSeek/OpenAI их не подхватывает.

**Защита шлюза:** обслуживает только подключения с адресов самого хоста (машины, запущенные через CLI, приходят именно так; соседи по LAN — нет), токен 192 бит и привязан к паре «машина + секрет», токен в URL или в нескольких заголовках отклоняется, можно ограничить HTTP-методы. Порт — `SMOLVM_WEB_GATEWAY_PORT` (7790). Машины с секретами-шлюзом стартуют через CLI, т.к. под `smolvm serve` хост недоступен.

**Хранение:** `vault.enc.json` (AES-256-GCM); ключ шифрования — в Keychain (macOS), DPAPI (Windows), Secret Service/`secret-tool` (Linux), иначе в файле `vault.key` (0600). Для headless-сервера можно задать `SMOLVM_WEB_VAULT_KEY` (64 hex).

Ограничения:
- Защита от агента *внутри машины*. Процессы на хосте под вашим пользователем могут получить ключ (как и из любого менеджера паролей).
- Если API вернёт ключ в теле ответа, машина его увидит — это подстановка, а не DLP.
- Клиент, игнорирующий `NO_PROXY` (busybox `wget`), отправит запрос к шлюзу через корпоративный прокси — туда уйдёт токен машины, а не ключ. curl, Python, Node учитывают `NO_PROXY`.
- Машина с подстановкой smolvm стартует через API и не видит корпоративный прокси/шлюз — не смешивайте режимы на одной машине за прокси.

## Создание машины по Smolfile

«Создать» → профиль **«Из Smolfile»** → вставьте Smolfile или нажмите «Загрузить файл». Для относительных путей в `volumes` (`./src:/app`) укажите «Папку проекта».

```toml
image = "python:3.12-slim"
net = true
cpus = 2
memory = 2048
ports = ["8000:8000"]
volumes = ["./src:/app:ro"]
env = ["APP_ENV=dev"]
init = ["pip install fastapi uvicorn"]
cmd = ["sh", "-c", "while true; do sleep 3600; done"]

[network]
allow_hosts = ["pypi.org", "files.pythonhosted.org"]

[restart]
policy = "on-failure"
```

smolvm-web разбирает Smolfile так же строго, как smolvm (неизвестный ключ — ошибка с номером строки), и создаёт машину через HTTP API — поэтому она полноценная машина `smolvm serve`: консоль, файлы, логи, агенты, фильтр «Сеть» и секреты работают как обычно. (`smolvm machine create -s` поставил бы машину вне реестра работающего `smolvm serve`: `exec` и файлы не работали бы до его перезапуска.)

- **`init`** выполняется один раз при первом запуске, от root, после записи настроек прокси и сертификатов, с `env` из Smolfile. Вывод — в уведомлении «Показать вывод». Если команда упала, init повторится при следующем запуске.
- **Сверху можно добавить** то, чем управляет smolvm-web: корпоративный прокси, фильтр «Сеть», секреты.
- **Не переносятся** (HTTP API smolvm их не принимает): `[secrets]` и `[[network.credentials]]` — используйте «Секреты»; `allow_host_patterns` — используйте `allow_hosts` или фильтр «Сеть». Ключи только для CLI (`user`, `[health]`, `[service]`, `[dev]`, `[auth]`, `stop_on_exit`, `gpu_vram`…) пропускаются с предупреждением.
- Если `cmd`/`entrypoint` не заданы, машина держится командой `sleep`, чтобы workload образа не завершался сразу.

### Модели и ключи

Привяжите к машине секрет DeepSeek, Anthropic, OpenAI или OpenRouter в режиме «Шлюз» — smolvm-web сам выставит переменные и конфиги каждому агенту, ключ в машину не попадает (машина видит токен и адрес шлюза на хосте):

| Агент | Как подключается ключ |
|---|---|
| Claude Code | Anthropic: `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`. DeepSeek: `ANTHROPIC_BASE_URL=<шлюз>/anthropic`, `ANTHROPIC_AUTH_TOKEN`, модель `deepseek-flash` |
| OpenCode | `~/.config/opencode/opencode.json`: провайдеры с `baseURL={env:…_BASE_URL}`, модель по умолчанию `deepseek/deepseek-flash` |
| Harness | `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL=<шлюз>/anthropic` |
| Codex | `~/.codex/config.toml`: провайдер `smolvm` (`base_url=<шлюз>`, `env_key=OPENAI_API_KEY`, Responses API), `/work` помечен доверенным. Без ключа OpenAI — `codex login` в терминале (ChatGPT) |
| Pi | `~/.pi/agent/models.json`: `baseUrl` встроенных провайдеров `deepseek`/`anthropic`/`openai` указывает на шлюз; `settings.json` → `defaultProvider` |
| Hermes | переменные `DEEPSEEK_*`, `ANTHROPIC_*`, `OPENROUTER_*`, `OPENAI_*` (ключ и `_BASE_URL`), провайдер выбирается один раз: `hermes config set model.provider …` |

**Локальная модель.** Если к машине привязан секрет «Локальная модель» с заполненным полем «Модель», он важнее облачных провайдеров для OpenCode, Pi и Hermes:

| Агент | Что настраивается |
|---|---|
| OpenCode | провайдер `local` (`@ai-sdk/openai-compatible`, `baseURL={env:LOCAL_LLM_BASE_URL}`, `apiKey={env:LOCAL_LLM_API_KEY}`), модель по умолчанию `local/<модель>` |
| Pi | провайдер `local` в `models.json` (`api: openai-completions`, `apiKey: $LOCAL_LLM_API_KEY`), `settings.json` → `defaultProvider: local`, `defaultModel` |
| Hermes | `model.provider custom`, `model.base_url`, `model.api_key ${LOCAL_LLM_API_KEY}`, `model.default`; применяется снова при смене модели или адреса |

Claude Code, Codex и Harness с локальными моделями не работают (им нужны Anthropic API или OpenAI Responses API). Модели с маленьким контекстом и без поддержки tool calling агентами пользуются плохо: берите модели от ~14B с инструментами и контекстом от 32k (в Ollama — `OLLAMA_CONTEXT_LENGTH=32768`). Отвязали секрет — агенты вернутся к облачному провайдеру при следующем запуске.

Конфиги пишутся при запуске агента, только если файла ещё нет или он создан smolvm-web (по метке): собственные настройки пользователя не перезаписываются. Модель можно сменить в самом агенте (`/model` в Claude Code и Pi, выбор модели в opencode, `hermes model`, `codex -m`).

### Провайдеры (серверы вендоров)

У каждого агента есть адреса вендора, к которым он обращается напрямую — минуя шлюз секретов: вход по подписке или OAuth, API при ключе в режиме «Переменная», каталоги моделей, обновления.

| Агент | Серверы вендора (порт 443) |
|---|---|
| Claude Code | `api.anthropic.com` (API), `claude.ai` (вход по подписке), `console.anthropic.com` (вход через Console) |
| OpenCode | `opencode.ai` (Zen, вход, обновления), `models.dev` (каталог моделей) |
| Harness | `api.deepseek.com` |
| Codex | `api.openai.com` (API), `auth.openai.com` (вход), `chatgpt.com` (подписка ChatGPT) |
| Pi | `pi.dev` (каталог моделей, `/login`, обновления) |
| Hermes | `inference-api.nousresearch.com` (Nous Portal API), `portal.nousresearch.com` (вход), `hermes-agent.nousresearch.com` (обновления) |

- **По умолчанию разрешены.** Для машины под фильтром «Сеть» серверы вендоров её агентов разрешены автоматически (в журнале — «сервер вендора: …»), на странице «Сеть» у машины видно «+ провайдеры: N». Подключили агента позже — его серверы добавятся сами.
- **Отзыв вручную.** Страница «Сеть» → карточка «Провайдеры» → «Отозвать»: фильтр сразу начинает блокировать адрес, без перезапуска машины. «Вернуть» снова разрешает. Каждое изменение записывается в аудит.
- Отзыв действует только при включённом фильтре «Сеть» — без него машина ходит в интернет без ограничений (блок подсказывает и включает фильтр одной кнопкой). Режим «Только разрешённое» сам включает изоляцию: обойти фильтр нельзя.
- Если адрес вендора нужен, но вы его отозвали, а в списке правил он разрешён явно — действует разрешение из списка: отзыв убирает только правило вендора.

### Устройство

Терминальные агенты (Claude Code, OpenCode TUI, Codex, Pi, Hermes, bash) работают в [ttyd](https://github.com/tsl0922/ttyd) с паролем, OpenCode web — с `OPENCODE_SERVER_PASSWORD`, Harness — со своим одноразовым токеном (dsh слушает только loopback машины, поэтому рядом запускается ретранслятор). Порт машины публикуется на `127.0.0.1` хоста, а браузер ходит через прокси smolvm-web на соседнем порту (`<порт>+10000`): он подставляет пароль, пропускает WebSocket и отклоняет чужие `Host`/`Origin`. Напрямую опубликованный порт без пароля отвечает 401.

**За корпоративным прокси / с фильтром «Сеть»** установке нужны: `deb.debian.org`, `security.debian.org` (apt), `registry.npmjs.org` (npm), `github.com` и `*.githubusercontent.com` (ttyd), для Hermes — ещё `hermes-agent.nousresearch.com`, `hermes-assets.nousresearch.com`, `pypi.org`, `files.pythonhosted.org`. При создании машины с профилем и фильтром эти правила добавляются автоматически. Доступ к модели по ключу из «Секретов» идёт через шлюз на хосте, отдельно разрешать API провайдера машине не нужно.

## Песочницы

Стартовая страница **Рабочие места** (`#/work`) — повседневный запуск: рабочее место = профиль агента + шаблон + агент, с которыми он открывается (запоминаются при создании и при каждом открытии). Управление шаблонами, профилями и ревью — на странице **Песочницы** (`#/sandbox`). Каждое открытие — чистая машина из шаблона; при закрытии она удаляется. Между песочницами живёт только **профиль агента** — файлы на хосте.

**Шаблон** — `smolvm machine checkpoint` машины с установленными агентами (RAM и диски). Подготовьте обычную машину с пресетом агента: секреты, фильтр «Сеть», нужные пакеты. Дождитесь установки агентов → «Шаблоны» → выберите машину → «Создать шаблон». Машина перезапускается с поддержкой ветвления (иначе smolvm на macOS не делает чекпоинт). Нельзя: папки хоста (директории), GPU/CUDA, том корпоративных сертификатов для скачивания образа. После обновления агентов в исходной машине — «Обновить».

**Открытие** («Открыть песочницу»: шаблон, профиль, агент) занимает несколько секунд:
1. машина создаётся из чекпоинта через API (её знает `smolvm serve`) с новыми портами и паролями агентов;
2. получает правила фильтра «Сеть» и секреты шаблона — со своими токенами фильтра и шлюза;
3. запускается как обычная машина (через CLI, если нужны фильтр или шлюз на хосте);
4. в домашнюю папку агента записываются файлы профиля поверх шаблона;
5. при выборе агента он сразу открывается в новой вкладке.

В списке «Машины» у неё метка «песочница»; консоль, файлы, агенты и рабочие копии работают как обычно. Рабочая папка `/work` каждый раз пустая.

**Профиль** — что сохраняется:

| Агент | Файлы |
|---|---|
| Claude Code | `~/.claude/CLAUDE.md`, `settings.json`, `skills/`, `agents/`, `commands/`, `output-styles/`, `hooks/`, память проектов `projects/*/memory/`; из `~/.claude.json` — только `mcpServers` |
| OpenCode | `~/.config/opencode/` (`opencode.json` с MCP, `AGENTS.md`, `agent/`, `command/`, `plugin/`) |
| Codex | `~/.codex/config.toml` (MCP), `AGENTS.md`, `skills/`, `prompts/` |
| Pi | `~/.pi/agent/`: `settings.json`, `models.json`, `AGENTS.md`, `SYSTEM.md`, `skills/`, `prompts/`, `extensions/`, `themes/` |
| Hermes | `~/.hermes/config.yaml`, `SOUL.md`, `memories/`, `skills/` |

Не сохраняются никогда: входы и токены (`auth.json`, `.credentials.json`, `.env`), сессии, кэши, `node_modules`, `.git`. Ключи моделей приходят из «Секретов» через шлюз. Файл больше 2 МБ (или сверх 30 МБ на профиль) пропускается — об этом сказано в ревью. Профиль можно начать пустым или «из машины» (взять текущие настройки уже настроенного агента), посмотреть и поправить его файлы прямо на странице.

**Закрытие.** «Закрыть» забирает файлы профиля из машины и удаляет её. Изменения (добавлен / изменён / удалён) появляются в «Изменения профиля на проверку» с diff по каждому файлу: «Сохранить в профиль» — выбранные или все, «Отклонить» — профиль остаётся как был. Skills, хуки, MCP-серверы и настройки агентов помечены «проверьте»: это исполняемая конфигурация, и вредная запись, сохранённая один раз, запускалась бы в каждой следующей песочнице. Для доверенного профиля ревью можно выключить (флажок «без ревью»). «Без сохранения» — просто удалить машину.

Свой `opencode.json` и `~/.codex/config.toml` smolvm-web не затирает: в `opencode.json` обновляются только `provider`/`model`, а в `config.toml` — блок между `# smolvm-web` и `# smolvm-web end`; MCP-серверы и остальное сохраняются.

## Страховка для агентов

### Ревью изменений (страница «Директории» → вкладка «Изменения агента»)

Агент получает не саму папку хоста, а её **рабочую копию** внутри машины. Всё, что он меняет, остаётся в машине, пока вы не нажмёте **«Применить»** — целиком, по выбранным файлам или по одному после просмотра diff. **«Отклонить»** возвращает в машине версию файла с хоста.

- Копия делается упаковкой папки (tar) и загрузкой в машину, а не монтированием: staged-монтирования smolvm сами копируют изменения на хост при остановке машины — без ревью.
- Изменения считаются по SHA-256 относительно манифеста на момент копирования. **Конфликт** — файл изменился и в машине, и на хосте; применение перезапишет хост, поэтому спрашивается подтверждение.
- «Подтянуть с хоста» обновляет в машине файлы, которые агент не трогал, а на хосте они изменились.
- Исключения по умолчанию: `.git`, `node_modules`, `.venv`, `__pycache__`, `dist`, `target` и т.п.
- Запись на хост атомарная, только внутри выбранной папки; symlink-компоненты пути и `..` отклоняются; символические ссылки не применяются автоматически.

### Режим обучения для allow list

«Сеть» → «Машины», режим **«Запись адресов»**: фильтр временно разрешает всё и запоминает, куда ходила машина (адреса хоста и внутренней сети по-прежнему только по явному правилу). Кнопка **«Сделать правилами…»** показывает собранные хосты — снимите лишние, при желании замените хост на `.домен`, и одной кнопкой они станут списком, подключённым к машине; обучение выключится.

### Аудит (страница «Аудит»)

- **Журнал действий**: команды exec (консоль, init) с кодом выхода, запуски/остановки/удаления машин, загрузки файлов, применение и отклонение в ревью (какие файлы), изменения секретов (без значений), правил сети, директорий и настроек. Кто — `ui@<адрес>`, `smolvm-web` для автоматических действий, `… → агент` для задач.
- **Изменения файлов** в папках хоста, подключённых к работающим машинам на запись (`fs.watch`). Источник — машина или человек на хосте — по файловой системе не различить; в записи перечислены машины с доступом на запись.
- Команды, которые агент выполняет внутри машины сам, smolvm не сообщает — их след: сетевой журнал и изменения файлов.
- Хранение: `audit.log` (JSON lines, ротация 10 МБ), экспорт в JSONL с кнопки.
- **Целостность**: записи связаны в цепочку — каждая хранит `prev` (хэш предыдущей) и `hash` = HMAC-SHA256 по ключу `audit.key` (32 байта, `0600`, в каталоге настроек). Кнопка **«Проверить целостность»** проходит `audit.log.1` и `audit.log` и сообщает, если запись изменена, удалена, вставлена или хвост журнала обрезан. Записи, сделанные до появления цепочки, считаются «без подписи» и показываются отдельно. Ключ защищает от правки журнала без доступа к каталогу настроек; для защиты от администратора хоста отправляйте журнал в SIEM.
- **SIEM** («Настройки» → «Аудит и SIEM»): syslog RFC 5424 (UDP/TCP, сообщение — JSON, facility local0–7) и/или HTTP POST пачек JSON (Splunk HEC, Elastic, Graylog и т.п., заголовок Authorization хранится только на сервере). Сетевые события фильтра — по выбору: только блокировки или все.
- **Оповещения** (там же): N заблокированных соединений одной машины за M секунд → уведомление в интерфейсе, запись в журнал, SIEM и веб-хук (POST JSON с полем `text`).

## Изоляция ИИ-агентов

### Сеть: allow list (egress-фильтр)

Страница **Сеть** (`#/egress`). На хосте работает фильтрующий HTTP(S)-прокси smolvm-web (порт `SMOLVM_WEB_EGRESS_PORT`, по умолчанию 7791). Машине с включённым фильтром в `HTTP(S)_PROXY` подставляется адрес этого прокси с её собственным токеном; каждое соединение сверяется с allow list машины и уходит в интернет хоста — через корпоративный прокси, если он настроен, иначе напрямую.

| Что | Как |
|---|---|
| Правила | `api.example.com` — ровно хост; `.example.com` — хост и поддомены; `*.example.com` — только поддомены; `10.0.0.0/8`, `192.0.2.10` — IP; `*` — любой. Порты: `443` (по умолчанию), `443,80`, `8000-8100`, `*`. Можно вставить URL — хост и порт извлекутся. |
| Списки | Именованные наборы правил («Общий», «LLM API», …) с шаблонами: PyPI, npm, GitHub, Docker Hub, apt/apk, Go, crates.io, Hugging Face, OpenAI, Anthropic, DeepSeek, OpenRouter, Gemini. Машина подключает списки и может иметь собственные правила. Отмеченные «подключать к новым машинам» включаются автоматически. |
| Журнал (отдельная страница) | Все соединения (разрешено/заблокировано, правило, трафик, путь — через корп. прокси или напрямую). Заблокированные собираются в блок «Разрешить»: хост или домен целиком добавляется в список или в правила машины одной кнопкой. Файл: `egress.log` в каталоге настроек. |
| Применение | Правила — сразу, без перезапуска. Включение фильтра для существующей машины — сразу для консоли/exec и профиля гостя (profile.d, pip, npm, apt, git), для основного процесса машины — при следующем запуске через smolvm-web (`smolvm machine update --env`). |
| Защита хоста | Адреса хоста, loopback, link-local (169.254.x — metadata), частные сети доступны только по явному правилу IP/CIDR — даже если разрешённое имя на них резолвится; `*` их не открывает. Без токена — 407, с чужих адресов (LAN) — 403. |
| Жёсткая изоляция | Фильтр видят только программы, учитывающие `HTTP(S)_PROXY`. В режиме «Только разрешённое» (если не выбрано «Без изоляции…») smolvm получает egress-политику «только IP хоста» (`allowedCidrs`), так что в обход фильтра наружу не выйти. Применяется при создании или при старте остановленной машины через smolvm-web. Учтите: машине доступны и другие сервисы хоста на внешнем интерфейсе. |
| Образы | Образ при старте качается отдельным токеном, которому дополнительно разрешены реестры (список — в настройках страницы; для Docker Hub это `registry-1.docker.io`, `auth.docker.io` и CDN `production.cloudflare.docker.com`, `production.cloudfront.docker.com`). Если скачивание всё же упрётся в запрет («…: Forbidden»), сообщение при запуске скажет, кто запретил: фильтр smolvm-web или корпоративный прокси. |

Ограничения: HTTPS не расшифровывается — фильтр работает по хосту и порту, не по пути. Машины с подстановкой smolvm (`substitute`) стартуют через API и до фильтра не достают. Если IP хоста сменился, жёсткая политика обновится при следующем запуске.

### Директории и права пользователей

Страница **Директории** (`#/dirs`) — какие папки этого компьютера видят агенты.

**Дать доступ к папке** — одна кнопка (на странице, в блоке «Папки агента» на вкладке «Обзор», во вкладке «Агенты», в окне создания машины и у песочниц). Вы выбираете:

- **папку** (путь с подсказками; сразу проверяется, можно ли её давать);
- **машину**;
- **режим**:
  - **только чтение** — папка подключается read-only на уровне компьютера, писать не может никто в машине, даже root;
  - **рабочая копия с ревью** — в машину копируется содержимое, изменения агента попадают на компьютер только после «Применить» (см. [ревью](#ревью-изменений-страница-директории--изменения-агента));
  - **чтение и запись** — агент меняет файлы напрямую.

Путь в машине по умолчанию — `/work/<имя папки>`. smolvm-web сам разрешает папку, подключает её, выдаёт права всем пользователям машины (агенты работают от `node`), предлагает перезапустить машину, если нужно, и проверяет доступ изнутри. У каждой папки виден статус: «✓ работает», «нужен перезапуск» (с кнопкой), «подключится при запуске» или причина, почему агент не получил доступ. Режим меняется в той же строке; при переходе с рабочей копии на папку непримененные изменения копии теряются (UI спрашивает).

**Запись и владелец папки.** Монтирование сохраняет владельца с компьютера: писать может только пользователь с тем же uid, что бы ни разрешала машина. Агенты работают от `node` (uid 1000), а на macOS ваши папки обычно принадлежат uid 501. Поэтому, когда агенту выдана запись, smolvm-web при запуске машины меняет uid пользователя `node` на uid владельца папки (`usermod`, файлы в `/home/node`, `/work`, `/tmp` переходят на новый uid). Агент пишет в папку как вы, и новые файлы на компьютере принадлежат вам. Ограничения: агенты в этот момент должны быть остановлены (это так сразу после перезапуска); если папки на запись принадлежат разным пользователям, писать агент сможет только в одну; в папку, принадлежащую root, агент не пишет — диалог предупреждает. Остальные пользователи машины в такой папке только читают.

**Тома smolvm** — поле в «Дополнительно» окна создания машины (`host:guest[:ro]`) и `volumes` в Smolfile: папка подключается как есть, флагом `-v` smolvm. Без проверки доступа агента, без ревью; изменить — только пересозданием машины. Такие тома видны в «Папках агента» с меткой «том smolvm». На них действует тот же запрет, что и в «Дать доступ к папке»: ключи (`~/.ssh`, `~/.aws`…), домашняя папка целиком, системные пути и настройки smolvm-web не подключаются; в строгом режиме — только папки из списка разрешённых. Нужны для Smolfile и случаев вроде «программе в образе нужен том по определённому пути»; агенту папку лучше давать через «Дать доступ к папке».

**Вкладка «Разрешённые папки»** — сюда папки попадают сами при выдаче доступа. Нельзя добавить корень диска, домашнюю директорию целиком, системные пути и места с ключами (`~/.ssh`, `~/.aws`, `~/.kube`, `~/.docker`, настройки smolvm-web…). Каталог настроек smolvm-web (там хранилище секретов) не монтируется никогда. **Строгий режим**: машинам можно давать только папки из списка (и их подпапки), не шире уровня «Не больше, чем».

**Права по отдельным пользователям машины** (разный доступ к одной папке для нескольких пользователей Linux в машине) задаются только через API: `PUT /ui/machines/<имя>/dirs` с `{"users": [{"name", "uid"}], "dirs": [{"id", "guestPath", "access": {"<пользователь>|*": "rw|ro|none"}}]}`, проверка — `POST /ui/machines/<имя>/dirs/verify`. Агенты работают от одного пользователя `node`, поэтому для них это не нужно.

Как обеспечивается:

- **Хост**: каждая директория монтируется в машину до двух раз — представление на запись (если кому-то нужна запись) и read-only представление (если кому-то нужно только чтение). Read-only обеспечивает хост: при «максимуме» «только чтение» не пишет даже root в машине.
- **Гость**: представления лежат в `/.smolvm-dirs/<имя>/{rw,ro}/data` за «шлюзами» — каталогами 0700 с POSIX ACL для нужных пользователей (пакет `acl` ставится в машину автоматически; без него — один пользователь на представление). smolvm exec сбрасывает дополнительные группы, поэтому группы не используются. Путь в машине (`/work`) — ссылка на самое широкое представление; у каждого пользователя есть `~/work` на своё; при наличии записи read-only представление ещё и в `/work-ro`.
- Смена прав внутри уже смонтированных представлений применяется сразу. Новая директория или новое представление требуют перезапуска (кнопка «Перезапустить сейчас»): smolvm меняет монтирования только у остановленной машины, smolvm-web делает это `smolvm machine update --volume` прямо перед стартом.

Ограничения: **root в машине обходит права гостя** — запускайте агентов от обычных пользователей (поле «user» в консоли, `"user"` в API exec). Монтирование сохраняет владельца с хоста: писать может пользователь с uid владельца директории на хосте (UI подсказывает uid). При самом первом запуске шлюзы закрываются сразу после старта, а не до него.

## Контроль агентов

### Подтверждение человеком

Необратимые действия ждут решения человека: в левом нижнем углу появляется карточка с таймером, в заголовке вкладки — число ожидающих. Нет ответа за 120 секунд — отказ. Одинаковые запросы (один хост, один вызов API) делят одну карточку. Каждое решение пишется в аудит.

- **Вызовы API через шлюз секретов.** У секрета в режиме «шлюз» поле **«Подтверждать»** — правила вида `МЕТОД путь`, через запятую: `DELETE *`, `PUT /repos/*/merge`, `POST /repos/*/releases`, `*` (метод) и `*` в пути — шаблоны. Подходящий запрос держится до решения (тело не читается, пока ждёт), «Запретить» — ответ 403. В шаблоне GitHub правила заполнены: удаления, merge, релизы, деплои, изменение веток.
- **Неизвестные адреса в сети.** «Сеть» → «Машины», галка **«Спрашивать о незнакомых адресах»** в карточке машины (включает фильтр): соединение не по правилам не отклоняется сразу, а ждёт решения — **«На 10 минут»** (временное разрешение хоста и порта), **«Всегда»** (правило машины), **«Запретить»**. Скачивание образов и адреса хоста не спрашиваются.

### Kill switch

- **«Изолировать»** (в шапке машины): разрывает все открытые соединения машины через фильтр, отклоняет её ожидающие подтверждения, меняет токены шлюза секретов (старые больше не работают), ставит машину на паузу. Пока машина изолирована, фильтр и шлюз ей отказывают (403), а запуск, продолжение и перезапуск через smolvm-web блокируются (409). Состояние хранится в `isolation.json` и переживает перезапуск smolvm-web.
- **«Снять изоляцию»** — машина остаётся на паузе, продолжите её вручную. Агентов перезапустите: их токены шлюза сменились.
- **«Остановить всех агентов»** (щит в заголовке списка машин) — то же для всех работающих машин сразу.
- Сетевой доступ машины идёт через фильтр и шлюз smolvm-web, поэтому изоляция действует через них и паузу; программа, ходящая в сеть мимо прокси, останавливается паузой (или не выходит наружу при «Жёстко»).

### Лимиты

Блок **«Лимиты»** на вкладке «Обзор» машины (0 — без ограничения):

| Лимит | Как действует |
|---|---|
| Процессов агента | `ulimit -u` для пользователя агента; не меньше 32. Применяется со следующего запуска агента. |
| Минут работы агента | smolvm-web проверяет раз в 30 секунд и останавливает агента, проработавшего дольше, с оповещением. |
| Запросов API в день | Счётчик запросов через шлюз секретов, сбрасывается в полночь; сверх лимита — 429. Сохраняется на диск при каждом запросе. |

Хранение — `limits.json`. CPU, память и диск ограничиваются ресурсами самой машины.

### Риск утечки («смертельная триада»)

Агент опасен, когда у него одновременно есть **доступ к приватным данным** (секреты, подключённые директории и папки хоста), **источник недоверенного ввода** (сеть: веб-страницы, issues, письма могут содержать prompt injection) и **канал утечки** (выход в интернет без фильтра или в режиме обучения). Блок **«Риск утечки»** на вкладке «Обзор» показывает каждое звено одним из трёх уровней: **●** открыто, **◐** ограничено, **○** закрыто. Куда машина может ходить, считается по факту:
- политика smolvm: «только этот компьютер» — интернета нет; список хостов или диапазонов — ограничено;
- фильтр «Сеть»: только разрешённые адреса — ограничено, режим «Запись адресов» или правило «*» — открыто;
- изоляция: фильтр без изоляции можно обойти (программа без прокси выйдет напрямую), поэтому выход наружу в таком режиме считается открытым.

«Все три звена» — это приватные данные плюс открытый выход наружу. Тогда вверху вкладки появляется предупреждение и кнопка **«Разорвать»**: она включает фильтр «Сеть», и наружу остаются только разрешённые адреса. Если данные есть, а сеть ограничена, блок показывает «ограничено». Если состояние изменится при следующем запуске (например, фильтр выключен, но машину пока держит оставшаяся изоляция), блок об этом предупреждает.

## Безопасность

`smolvm serve` **не имеет аутентификации**: доступ к API = shell на хосте. Поэтому прокси:

- слушает только `127.0.0.1`;
- отклоняет запросы с чужим `Host` (DNS rebinding) и `Origin`;
- требует заголовок `X-Smolvm-UI: 1` для изменяющих запросов.

Настройки (могут содержать пароль прокси) хранятся с правами `0600`. Не публикуйте порт наружу.

Файлы в каталоге настроек: `settings.json`, `state.json`, `vault.enc.json` (секреты), `egress.json` (allow list и токены машин), `dirs.json` (директории и права), `egress.log` (журнал соединений), `audit.json` / `audit.log` (аудит), `review.json` (рабочие копии), `agents.json`, `smolfile.json`, `audit.key` (ключ цепочки аудита), `isolation.json` (изолированные машины), `limits.json` (лимиты и счётчики).

## Замечания

- Остановка `smolvm serve` **не останавливает машины**.
- Консоль не интерактивная (нет TTY): для полноценного shell — `smolvm machine exec -it --name <имя> -- sh`.
