## Первые шаги

Типовая настройка изолированного агента:

1. **Сеть** (если вы за корпоративным прокси): кнопка настроек в шапке → «Сеть, прокси и сертификаты» → «Определить автоматически» → «Проверить» → при TLS-инспекции включите «Доверять корпоративным сертификатам» → «Сохранить». См. [Корпоративный прокси](#корпоративный-прокси).
2. **Ключ модели**: «Секреты» → «Добавить секрет» → шаблон (DeepSeek, Anthropic, OpenAI…) → режим «Шлюз smolvm-web». Ключ не попадает в машину. См. [Секреты и API-ключи](#секреты-и-api-ключи).
3. **Allow list**: страница «Доступ в сеть» → создайте или дополните список разрешённых ресурсов (есть шаблоны PyPI, npm, GitHub и др.). Для первичной настройки удобен [режим обучения](#режим-обучения-для-allow-list). См. [Доступ в сеть](#доступ-в-сеть-allow-list-egress-фильтр).
4. **Директории**: страница «Директории» → добавьте папки хоста, которые можно отдавать агентам, с максимумом прав. Для работы с кодом лучше [рабочая копия с ревью](#ревью-изменений-вкладка-изменения), чем прямое монтирование на запись. См. [Директории и права](#директории-и-права-пользователей).
5. **Машина**: «+ Машина» → профиль агента (Claude Code, OpenCode, DeepSeek Harness) или «Из Smolfile» → отметьте секреты, фильтр «Доступ в сеть», при необходимости жёсткую изоляцию и директории → «Создать». Агенты установятся при первом запуске. См. [Профили и ИИ-агенты](#профили-и-ии-агенты).
6. **Работа**: вкладка «Агенты» → «Запустить» (агент откроется в новой вкладке) или «Задача без интерфейса». Включите «Снимок перед запуском», чтобы откатываться одной кнопкой.
7. **Контроль**: страница «Журнал» — куда ходят машины и что заблокировано; «Аудит» — команды, изменения файлов, экспорт в SIEM и оповещения; вкладка «Изменения» — что агент сделал с рабочей копией.

## Параметры запуска

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SMOLVM_API` | macOS/Linux: `unix:///tmp/smolvm.sock`<br>Windows: `http://127.0.0.1:18899` | адрес `smolvm serve` |
| `SMOLVM_BIN` | `smolvm` | путь к бинарнику (`C:\tools\smolvm.exe`); настройка «Путь к бинарнику smolvm» в интерфейсе важнее |
| `PORT` | `7777` | порт веб-интерфейса |
| `SMOLVM_AUTOSTART` | — | `1` = то же, что `--autostart` |
| `SMOLVM_WEB_EGRESS_PORT` | `7791` | порт egress-фильтра (allow list) на хосте |
| `SMOLVM_WEB_HOME` | `~/.config/smolvm-web`, Windows: `%APPDATA%\smolvm-web` | настройки и лог `smolvm-serve.log` |
| `SMOLVM_WEB_GATEWAY_PORT` | `7790` | порт шлюза секретов на хосте |
| `SMOLVM_WEB_VAULT_KEY` | — | ключ хранилища секретов (64 hex) для headless-сервера без хранилища ключей ОС |

Пример: `PORT=7800 SMOLVM_BIN=/opt/smolvm/smolvm ./start.sh` (Windows: `set PORT=7800 && start.cmd`).

**Путь к smolvm в интерфейсе.** Кнопка **«Настройки»** (шестерёнка в шапке) → раздел «smolvm» → «Путь к бинарнику smolvm» (например `C:\smolvm\smolvm.exe` или `/opt/smolvm/smolvm`), «Проверить» запускает `<путь> --version`. Путь сохраняется в настройках и применяется сразу ко всем вызовам CLI; `smolvm serve`, запущенный `--autostart`, использует его при следующем запуске smolvm-web. Пустое поле — `SMOLVM_BIN` или `smolvm` из `PATH`.

### Особенности Windows

- smolvm на Windows не поддерживает Unix-сокет, поэтому API слушает loopback TCP `127.0.0.1:18899`. Нужна включённая Windows Hypervisor Platform.
- Вывод `smolvm serve` и `smolvm machine start` пишется в файл, а не в pipe: на Windows CLI иначе не возвращает управление.
- Монтирования принимают пути с буквой диска: `C:\Users\me\project:/work` или `D:/data:/data:ro`.
- «Определить автоматически» берёт системный прокси из `Internet Settings` (реестр), сертификаты — из хранилища Windows.

- **Право на символические ссылки обязательно.** smolvm распаковывает свой агентский rootfs из tar в `%LOCALAPPDATA%\smolvm\rootfs\` и без права на symlink (Режим разработчика или запуск от администратора) теряет `/sbin/init`: машины падают с `boot process exited (code 127)` / `Couldn't execute '/sbin/init': ENOENT`. smolvm-web проверяет это при запуске и в интерфейсе: показывает баннер и кнопку **«Починить»**, которая удаляет испорченную распаковку (только каталоги rootfs без `/sbin/init`), чтобы smolvm распаковал её заново. Перед починкой право на symlink должно уже быть.

Подробное развёртывание, автозапуск и частые проблемы — в [INSTALL.md](INSTALL.md).

## Корпоративный прокси

Кнопка **«Настройки»** (шестерёнка в шапке) (или индикатор в шапке) → «Сеть, прокси и сертификаты».

| Что | Как реализовано |
|---|---|
| Запуск и образы | При включённом прокси машина стартует через `smolvm machine start [--proxy … --no-proxy …]`: HTTP API smolvm при старте тянет образ без прокси, а `smolvm serve` ставит строгую egress-политику (`SMOLVM_EGRESS_FLOOR=strict`), при которой машины не видят хост и LAN — то есть и корпоративный прокси. Pull во вкладке «Образы» получает поле `proxy`. |
| Переменные в машине | `HTTP(S)_PROXY`, `NO_PROXY` (в обоих регистрах) добавляются в `env` при создании и в каждый `exec` из консоли/API. Явно заданные переменные не перезаписываются. |
| Настройка гостя после старта | `/etc/profile.d/smolvm-proxy.sh`, `/etc/pip.conf`, глобальный `npmrc`, `/etc/apt/apt.conf.d/95smolvm-proxy`, `git config --system http.proxy`. Для уже запущенной машины — кнопка «Применить прокси». |
| Прокси на `localhost` хоста (cntlm, px) | Внутри машины `localhost` — это сама машина, поэтому адрес переписывается на IP хоста. Прокси должен слушать этот интерфейс (`Gateway yes` в cntlm, `--gateway` в px). |
| TLS-инспекция | Bundle = публичные корневые (Mozilla) + сертификаты ОС + ваш PEM/файл. Кладётся в `/etc/smolvm-host-trust/ca-bundle.pem`, на него указывают `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `GIT_SSL_CAINFO` и др.; опционально заменяет системный bundle гостя (apk, apt, curl, wget). |
| Скачивание образа за TLS-инспекцией | Образ при старте качает `crane` внутри гостевого агента smolvm, до записи настроек в машину. С галочкой «Доверять им при скачивании образа» (по умолчанию включена) smolvm-web пишет тот же bundle в `<каталог настроек>/host-trust/ca-bundle.pem` и подключает его к машине read-only томом `/etc/smolvm-host-trust` — так же, как `--trust-host-certs` smolvm, который сам не умеет читать хранилище Windows. Том добавляется при создании, а у существующих машин — при следующем запуске через smolvm-web (`machine update --volume`). Ошибка `x509: certificate signed by unknown authority` при запуске показывается с подсказкой, что включить. Цена: smolvm не делает снимки машин с томами хоста — когда образ уже скачан, галочку можно выключить, и том отключится при следующем запуске. |
| Проверка | «Проверить» делает `CONNECT` к docker.io / pypi.org / npmjs.org через прокси с хоста и по адресу, который увидят машины. |
| Исключения | NO_PROXY общий; на отдельной машине прокси можно выключить (вкладка «Обзор» или чекбокс при создании). |

Если `smolvm serve` запускается через `--autostart` при включённом прокси, ему тоже передаются `HTTPS_PROXY`/`NO_PROXY` (запросы к реестрам со стороны хоста). После изменения прокси перезапустите smolvm-web, чтобы это применилось.

Альтернатива для образов — корпоративный реестр, см. [Корпоративные репозитории](#корпоративные-репозитории).

Ограничения: PAC-файлы не поддерживаются (укажите адрес прокси явно); логин/пароль в URL прокси видны процессам внутри машины.

## Корпоративные репозитории

Кнопка **«Настройки»** (шестерёнка в шапке) → «Корпоративные репозитории». Подходит для JFrog Artifactory, Sonatype Nexus, Harbor и любых других прокси-репозиториев. Все поля необязательны: заполните только то, что есть.

| Поле | Пример (Artifactory) | Что делает |
|---|---|---|
| Реестр образов | `artifactory.corp.local/docker-remote` | с галочкой «Брать образы Docker Hub из этого реестра» образы Docker Hub при создании машины переписываются: `node:22` → `artifactory.corp.local/docker-remote/library/node:22`, `docker.io/bitnami/redis` → `…/bitnami/redis`. Образы других реестров (`ghcr.io/…`) не меняются. Профили агентов тоже идут через реестр. |
| Пользователь / токен | `ci-bot` / API key или Identity token | логин к реестру образов: smolvm-web пишет `<каталог настроек>/docker/config.json` (ваш `~/.docker/config.json` + запись `auths`) и передаёт его smolvm через `DOCKER_CONFIG`, как после `docker login`. В машину логин не попадает. Токен хранится в `settings.json` (0600) и не отдаётся браузеру. |
| PyPI | `https://artifactory.corp.local/api/pypi/pypi-remote/simple` | `PIP_INDEX_URL` в консоли/exec и `index-url` в `/etc/pip.conf` (для `http://` — ещё `trusted-host`) |
| npm | `https://artifactory.corp.local/api/npm/npm-remote` | `NPM_CONFIG_REGISTRY` и `registry=` в глобальном `npmrc` (установка агентов тоже идёт через него) |
| apt: вместо deb.debian.org/debian и …/debian-security | `https://artifactory.corp.local/artifactory/debian-remote` | заменяет адреса в `/etc/apt/sources.list` и `/etc/apt/sources.list.d/debian.sources` (оригиналы — `*.smolvm-orig`) |
| Go | `https://artifactory.corp.local/artifactory/api/go/go-remote` | `GOPROXY` (+ `GONOSUMDB=*`), `/etc/profile.d/smolvm-go.sh` |
| GitHub releases | `https://artifactory.corp.local/artifactory/github-remote` (generic remote на `https://github.com`) | откуда качать бинарники с GitHub при установке агентов вместо `https://github.com`. Веб-терминал ttyd smolvm-web скачивает сам на этом компьютере (через корпоративный прокси, если он включён, или с этого зеркала) и загружает в машину, так что машине GitHub не нужен |

**Уже созданные машины.** Образ машины фиксируется при создании, а smolvm не умеет менять его у существующей машины. Машина, созданная до настройки реестра, продолжит качать образ с Docker Hub; без прямого доступа запуск упадёт (`crane manifest failed … index.docker.io … TLS handshake timeout`) — smolvm-web покажет, какой образ из реестра будет использован, и предложит создать машину заново. Машина, которая ни разу не запускалась, пуста — её можно просто удалить. (Встроенный в smolvm `mirror` для `docker.io` в `~/.config/smolvm/config.toml` не помогает: образ скачивается под именем зеркала и потом не находится.)

**ttyd без доступа к GitHub.** Веб-терминал — это бинарник ttyd с GitHub (в Debian bookworm пакета нет). При установке агентов smolvm-web берёт его так: файл `ttyd.x86_64` / `ttyd.aarch64` из папки `<каталог настроек>/bin` (например `%APPDATA%\smolvm-web\bin`), иначе скачивает на этом компьютере — с зеркала GitHub releases или с github.com (через корпоративный прокси, если он включён в настройках; для конкретной машины прокси при этом можно выключить) — и загружает в машину. Если у компьютера нет доступа ни туда, ни туда, скачайте `https://github.com/tsl0922/ttyd/releases/download/1.7.7/ttyd.x86_64` где получится, положите в эту папку и повторите установку.

**Логин внутри машины.** По умолчанию пакетные репозитории читаются анонимно. Если им нужен логин, включите «Передавать пользователя и токен в машину»: тогда он добавляется в URL pip и Go, в `npmrc` (`_auth`) и в `/etc/apt/auth.conf.d/smolvm.conf`. Агент в машине сможет прочитать этот токен — выдайте для этого отдельную учётную запись только на чтение.

**Сеть.** Хосты репозиториев автоматически разрешены фильтру «Доступ в сеть» (все порты, источник «корпоративные репозитории»), в том числе когда они резолвятся во внутренние адреса; адреса самого хоста и `127.0.0.0/8` по-прежнему закрыты. **Сертификаты репозиториев.** Если хоть один пакетный репозиторий указан по `https://`, smolvm-web передаёт в машину CA bundle — публичные корни + сертификаты, которым доверяет этот компьютер (внутренний CA, которому доверяет браузер, там уже есть) + PEM из раздела сертификатов — даже при выключенных «корпоративных сертификатах». apt получает `Acquire::https::CaInfo` (`/etc/apt/apt.conf.d/95smolvm-ca`), а в slim-образах без пакета `ca-certificates` создаётся `/etc/ssl/certs/ca-certificates.crt` — иначе apt пишет `No system certificates available. Try installing ca-certificates`. Если CA репозитория нет в хранилище ОС (или Node.js старше 22.15 и не читает его), вставьте его PEM в «Настройки» → «Сеть, прокси и сертификаты».

При включённом корпоративном прокси запросы к репозиторию идут через него; если репозиторий во внутренней сети и прокси его не пропускает, добавьте его хост в NO_PROXY — тогда и фильтр, и машина пойдут к нему напрямую. За TLS-инспекцией или с внутренним CA репозитория включите корпоративные сертификаты (раздел выше).

Настройки гостя (pip, npm, apt, Go) применяются при запуске машины через smolvm-web и кнопкой «Применить прокси»; переменные консоли и exec — сразу. `smolvm serve`, запущенный через `--autostart`, видит логин к реестру сразу после сохранения; если вы запускаете `smolvm serve` сами, задайте ему `DOCKER_CONFIG=<каталог настроек>/docker`.

## Секреты и API-ключи

Ключ (DeepSeek, OpenAI, GitHub…) хранится в зашифрованном хранилище на хосте, а агент в машине может им **пользоваться, но не может его прочитать**. Значение не попадает ни в машину, ни в её запись в smolvm, ни в интерфейс (после сохранения оно не показывается).

| Режим | Что видит машина | Как работает | Когда |
|---|---|---|---|
| **Шлюз smolvm-web** | `DEEPSEEK_API_KEY=smolgw_…` (токен машины), `DEEPSEEK_BASE_URL=http://<IP хоста>:7790/g/deepseek` | SDK шлёт запрос на шлюз; шлюз проверяет токен, меняет его на ключ и отправляет на `https://api.deepseek.com` — **через корпоративный прокси**, если он настроен | По умолчанию за прокси |
| **Подстановка smolvm** | `DEEPSEEK_API_KEY=SMOL_PLACEHOLDER_…` | Родной [credential substitution](https://github.com/smol-machines/smolvm/blob/main/docs/credential-substitution.md): хост подменяет заглушку в HTTPS-заголовке, только к указанным хостам. Значения передаются в `smolvm serve` (`PUT /credential-values`) перед каждым стартом | Есть прямой интернет. Перехватчик smolvm ходит к API **без прокси** — за корпоративным прокси не работает |
| **Переменная** | значение как есть | Добавляется в команды консоли/exec | Только то, что программа должна прочитать сама (URL БД) |

Пример для агента (OpenAI-совместимый SDK, DeepSeek):

```python
from openai import OpenAI
import os
client = OpenAI(base_url=os.environ["DEEPSEEK_BASE_URL"], api_key=os.environ["DEEPSEEK_API_KEY"])
```

Как пользоваться: «Секреты» → «+ Добавить» (есть шаблоны DeepSeek/OpenAI/Anthropic/OpenRouter/Gemini/GitHub) → при создании машины отметьте секреты. Шлюз и переменные можно привязывать и к существующей машине (вкладка «Обзор»); подстановка задаётся только при создании. Ротация: измените значение — шлюз подхватывает сразу, подстановка — со следующего старта машины.

**Локальная модель (Ollama, vLLM, LM Studio, llama.cpp, свой DeepSeek).** «Секреты» → «Добавить секрет» → шаблон «Локальная модель (OpenAI-совместимая)»: режим «Шлюз», URL API — адрес OpenAI-совместимого сервера (`http://localhost:11434/v1` для Ollama, `http://localhost:8000/v1` для vLLM, `http://<сервер>:<порт>/v1` для машины в сети), галочка «Локальная модель / сервер по HTTP», значение — ключ сервера (если сервер без ключа — любая строка). Шлюз работает на хосте, поэтому `localhost` в URL — это сам хост: серверу модели не нужно слушать сетевой интерфейс. Машина получает `LOCAL_LLM_API_KEY` (токен) и `LOCAL_LLM_BASE_URL` (адрес шлюза); к HTTP-адресам шлюз ходит напрямую, без корпоративного прокси. Укажите поле «Модель» (имя модели на сервере, например `deepseek-r1:14b` для Ollama или `deepseek-ai/DeepSeek-R1-Distill-Qwen-14B` для vLLM) — тогда OpenCode, Pi и Hermes настроятся на неё сами (см. [Модели и ключи](#модели-и-ключи)). Нейтральные имена переменных выбраны специально: автонастройка под облачные DeepSeek/OpenAI их не подхватывает.

**Защита шлюза:** обслуживает только подключения с адресов самого хоста (машины, запущенные через CLI, приходят именно так; соседи по LAN — нет), токен 192 бит и привязан к паре «машина + секрет», токен в URL или в нескольких заголовках отклоняется, можно ограничить HTTP-методы. Порт — `SMOLVM_WEB_GATEWAY_PORT` (7790). Машины с секретами-шлюзом стартуют через CLI, т.к. под `smolvm serve` хост недоступен.

**Хранение:** `vault.enc.json` (AES-256-GCM); ключ шифрования — в Keychain (macOS), DPAPI (Windows), Secret Service/`secret-tool` (Linux), иначе в файле `vault.key` (0600). Для headless-сервера можно задать `SMOLVM_WEB_VAULT_KEY` (64 hex).

Ограничения:
- Защита от агента *внутри машины*. Процессы на хосте под вашим пользователем могут получить ключ (как и из любого менеджера паролей).
- Если API вернёт ключ в теле ответа, машина его увидит — это подстановка, а не DLP.
- Клиент, игнорирующий `NO_PROXY` (busybox `wget`), отправит запрос к шлюзу через корпоративный прокси — туда уйдёт токен машины, а не ключ. curl, Python, Node учитывают `NO_PROXY`.
- Машина с подстановкой smolvm стартует через API и не видит корпоративный прокси/шлюз — не смешивайте режимы на одной машине за прокси.

## Создание машины по Smolfile

«+ Машина» → профиль **«Из Smolfile»** → вставьте Smolfile или нажмите «Загрузить файл». Для относительных путей в `volumes` (`./src:/app`) укажите «Папку проекта».

```toml
image = "python:3.12-slim"
net = true
cpus = 2
memory = 2048
ports = ["8000:8000"]
volumes = ["./src:/app:ro"]
env = ["APP_ENV=dev"]
init = ["pip install fastapi uvicorn"]
cmd = ["sh", "-c", "while true; do sleep 3600; done"]

[network]
allow_hosts = ["pypi.org", "files.pythonhosted.org"]

[restart]
policy = "on-failure"
```

smolvm-web разбирает Smolfile так же строго, как smolvm (неизвестный ключ — ошибка с номером строки), и создаёт машину через HTTP API — поэтому она полноценная машина `smolvm serve`: консоль, файлы, логи, агенты, фильтр «Доступ в сеть» и секреты работают как обычно. (`smolvm machine create -s` поставил бы машину вне реестра работающего `smolvm serve`: `exec` и файлы не работали бы до его перезапуска.)

- **`init`** выполняется один раз при первом запуске, от root, после записи настроек прокси и сертификатов, с `env` из Smolfile. Вывод — в уведомлении «Показать вывод». Если команда упала, init повторится при следующем запуске.
- **Сверху можно добавить** то, чем управляет smolvm-web: корпоративный прокси, фильтр «Доступ в сеть», секреты.
- **Не переносятся** (HTTP API smolvm их не принимает): `[secrets]` и `[[network.credentials]]` — используйте «Секреты»; `allow_host_patterns` — используйте `allow_hosts` или фильтр «Доступ в сеть». Ключи только для CLI (`user`, `[health]`, `[service]`, `[dev]`, `[auth]`, `stop_on_exit`, `gpu_vram`…) пропускаются с предупреждением.
- Если `cmd`/`entrypoint` не заданы, машина держится командой `sleep`, чтобы workload образа не завершался сразу.

К существующей машине агентов можно подключить во вкладке «Агенты» (нужен Debian-образ с Node.js 22.19+; машина перезапустится, чтобы опубликовать порты).

**Вкладка «Агенты»**: «Запустить» поднимает агента и открывает его в новой вкладке браузера (без запроса пароля), «Открыть» — для уже работающего; флажок «автономно» запускает без подтверждений (Claude Code — `--dangerously-skip-permissions`, Codex — `--dangerously-bypass-approvals-and-sandbox`, Hermes — `--yolo`). «Задача без интерфейса» выполняет одну задачу с потоковым выводом:

| Агент | Команда задачи |
|---|---|
| Claude Code | `claude -p` (`--permission-mode acceptEdits`, или `--dangerously-skip-permissions` с «без подтверждений») |
| OpenCode | `opencode run` |
| DeepSeek Harness | `dsh headless` |
| Codex | `codex exec --skip-git-repo-check --sandbox workspace-write` (или `--dangerously-bypass-approvals-and-sandbox`) |
| Pi | `pi -p` |
| Hermes | `hermes -z` (одноразовый режим, подтверждения пропускаются) |

Агенты работают в машине от пользователя `node` в `/work`.

### Модели и ключи

Привяжите к машине секрет DeepSeek, Anthropic, OpenAI или OpenRouter в режиме «Шлюз» — smolvm-web сам выставит переменные и конфиги каждому агенту, ключ в машину не попадает (машина видит токен и адрес шлюза на хосте):

| Агент | Как подключается ключ |
|---|---|
| Claude Code | Anthropic: `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`. DeepSeek: `ANTHROPIC_BASE_URL=<шлюз>/anthropic`, `ANTHROPIC_AUTH_TOKEN`, модель `deepseek-flash` |
| OpenCode | `~/.config/opencode/opencode.json`: провайдеры с `baseURL={env:…_BASE_URL}`, модель по умолчанию `deepseek/deepseek-flash` |
| DeepSeek Harness | `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL=<шлюз>/anthropic` |
| Codex | `~/.codex/config.toml`: провайдер `smolvm` (`base_url=<шлюз>`, `env_key=OPENAI_API_KEY`, Responses API), `/work` помечен доверенным. Без ключа OpenAI — `codex login` в терминале (ChatGPT) |
| Pi | `~/.pi/agent/models.json`: `baseUrl` встроенных провайдеров `deepseek`/`anthropic`/`openai` указывает на шлюз; `settings.json` → `defaultProvider` |
| Hermes | переменные `DEEPSEEK_*`, `ANTHROPIC_*`, `OPENROUTER_*`, `OPENAI_*` (ключ и `_BASE_URL`), провайдер выбирается один раз: `hermes config set model.provider …` |

**Локальная модель.** Если к машине привязан секрет «Локальная модель» с заполненным полем «Модель», он важнее облачных провайдеров для OpenCode, Pi и Hermes:

| Агент | Что настраивается |
|---|---|
| OpenCode | провайдер `local` (`@ai-sdk/openai-compatible`, `baseURL={env:LOCAL_LLM_BASE_URL}`, `apiKey={env:LOCAL_LLM_API_KEY}`), модель по умолчанию `local/<модель>` |
| Pi | провайдер `local` в `models.json` (`api: openai-completions`, `apiKey: $LOCAL_LLM_API_KEY`), `settings.json` → `defaultProvider: local`, `defaultModel` |
| Hermes | `model.provider custom`, `model.base_url`, `model.api_key ${LOCAL_LLM_API_KEY}`, `model.default`; применяется снова при смене модели или адреса |

Claude Code, Codex и DeepSeek Harness с локальными моделями не работают (им нужны Anthropic API или OpenAI Responses API). Модели с маленьким контекстом и без поддержки tool calling агентами пользуются плохо: берите модели от ~14B с инструментами и контекстом от 32k (в Ollama — `OLLAMA_CONTEXT_LENGTH=32768`). Отвязали секрет — агенты вернутся к облачному провайдеру при следующем запуске.

Конфиги пишутся при запуске агента, только если файла ещё нет или он создан smolvm-web (по метке): собственные настройки пользователя не перезаписываются. Модель можно сменить в самом агенте (`/model` в Claude Code и Pi, выбор модели в opencode, `hermes model`, `codex -m`).

### Серверы вендоров

У каждого агента есть адреса вендора, к которым он обращается напрямую — минуя шлюз секретов: вход по подписке или OAuth, API при ключе в режиме «Переменная», каталоги моделей, обновления.

| Агент | Серверы вендора (порт 443) |
|---|---|
| Claude Code | `api.anthropic.com` (API), `claude.ai` (вход по подписке), `console.anthropic.com` (вход через Console) |
| OpenCode | `opencode.ai` (Zen, вход, обновления), `models.dev` (каталог моделей) |
| DeepSeek Harness | `api.deepseek.com` |
| Codex | `api.openai.com` (API), `auth.openai.com` (вход), `chatgpt.com` (подписка ChatGPT) |
| Pi | `pi.dev` (каталог моделей, `/login`, обновления) |
| Hermes | `inference-api.nousresearch.com` (Nous Portal API), `portal.nousresearch.com` (вход), `hermes-agent.nousresearch.com` (обновления) |

- **По умолчанию разрешены.** Для машины под фильтром «Доступ в сеть» серверы вендоров её агентов разрешены автоматически (в журнале — «сервер вендора: …»), на странице «Доступ в сеть» у машины видно «+ серверы вендоров: N». Подключили агента позже — его серверы добавятся сами.
- **Отзыв вручную.** Вкладка «Агенты» → блок «Серверы вендоров» → «Отозвать»: фильтр сразу начинает блокировать адрес, без перезапуска машины. «Вернуть» снова разрешает. Каждое изменение записывается в аудит.
- Отзыв действует только при включённом фильтре «Доступ в сеть» — без него машина ходит в интернет без ограничений (блок подсказывает и включает фильтр одной кнопкой). Для полной гарантии включите и «жёсткую изоляцию».
- Если адрес вендора нужен, но вы его отозвали, а в списке правил он разрешён явно — действует разрешение из списка: отзыв убирает только правило вендора.

### Устройство

Терминальные агенты (Claude Code, OpenCode TUI, Codex, Pi, Hermes, bash) работают в [ttyd](https://github.com/tsl0922/ttyd) с паролем, OpenCode web — с `OPENCODE_SERVER_PASSWORD`, DeepSeek Harness — со своим одноразовым токеном (dsh слушает только loopback машины, поэтому рядом запускается ретранслятор). Порт машины публикуется на `127.0.0.1` хоста, а браузер ходит через прокси smolvm-web на соседнем порту (`<порт>+10000`): он подставляет пароль, пропускает WebSocket и отклоняет чужие `Host`/`Origin`. Напрямую опубликованный порт без пароля отвечает 401.

**За корпоративным прокси / с фильтром «Доступ в сеть»** установке нужны: `deb.debian.org`, `security.debian.org` (apt), `registry.npmjs.org` (npm), `github.com` и `*.githubusercontent.com` (ttyd), для Hermes — ещё `hermes-agent.nousresearch.com`, `hermes-assets.nousresearch.com`, `pypi.org`, `files.pythonhosted.org`. При создании машины с профилем и фильтром эти правила добавляются автоматически. Доступ к модели по ключу из «Секретов» идёт через шлюз на хосте, отдельно разрешать API провайдера машине не нужно.

## Страховка для агентов

### Ревью изменений (вкладка «Изменения»)

Агент получает не саму папку хоста, а её **рабочую копию** внутри машины. Всё, что он меняет, остаётся в машине, пока вы не нажмёте **«Применить»** — целиком, по выбранным файлам или по одному после просмотра diff. **«Отклонить»** возвращает в машине версию файла с хоста.

- Копия делается упаковкой папки (tar) и загрузкой в машину, а не монтированием: смонтированные папки не дают делать снимки, а staged-монтирования smolvm сами копируют изменения на хост при остановке машины — без ревью.
- Изменения считаются по SHA-256 относительно манифеста на момент копирования. **Конфликт** — файл изменился и в машине, и на хосте; применение перезапишет хост, поэтому спрашивается подтверждение.
- «Подтянуть с хоста» обновляет в машине файлы, которые агент не трогал, а на хосте они изменились.
- Исключения по умолчанию: `.git`, `node_modules`, `.venv`, `__pycache__`, `dist`, `target` и т.п.
- Запись на хост атомарная, только внутри выбранной папки; symlink-компоненты пути и `..` отклоняются; символические ссылки не применяются автоматически.

### Снимки и откат (вкладка «Снимки»)

Снимок — `smolvm machine checkpoint`: память, процессы и диски, пауза машины — доли секунды. **«Откатить»** пересоздаёт машину из снимка под тем же именем через API smolvm; агенты, секреты, «Доступ в сеть» и состояние рабочих копий сохраняются. Перед откатом текущее состояние сохраняется **страховочным снимком**, и если восстановленная машина не запустится, она возвращается из него.

- Во вкладке «Агенты» включите **«Снимок перед запуском»** — снимок перед каждым запуском агента и задачей.
- Машины с агентами и машины, где включены снимки, запускаются с ветвлением (`--branchable`, на macOS обязательно для снимков).
- smolvm не снимает машины с подключёнными папками хоста, GPU/CUDA — используйте рабочие копии вместо монтирования.
- Новые машины smolvm-web создаёт с явным `networkBackend: virtio-net`: у машин со «неявным» сетевым режимом без портов smolvm восстанавливает снимок с другим сетевым устройством, и откат не запускается — для таких машин вкладка объясняет это заранее.
- Хранится последних 10 снимков на машину; файлы — в каталоге настроек (`checkpoints/`).

### Режим обучения для allow list

Страница «Доступ в сеть», колонка **«Обучение»**: фильтр временно разрешает всё и запоминает, куда ходила машина (адреса хоста и внутренней сети по-прежнему только по явному правилу). Кнопка **«Собрать»** показывает собранные хосты — снимите лишние, при желании замените хост на `.домен`, и одной кнопкой они станут списком, подключённым к машине; обучение выключится.

### Аудит (страница «Аудит»)

- **Журнал действий**: команды exec (консоль, задачи агентам, init) с кодом выхода, запуски/остановки/удаления машин, загрузки файлов, применение и отклонение в ревью (какие файлы), снимки и откаты, изменения секретов (без значений), правил сети, директорий и настроек. Кто — `ui@<адрес>`, `smolvm-web` для автоматических действий, `… → агент` для задач.
- **Изменения файлов** в папках хоста, подключённых к работающим машинам на запись (`fs.watch`). Источник — машина или человек на хосте — по файловой системе не различить; в записи перечислены машины с доступом на запись.
- Команды, которые агент выполняет внутри машины сам, smolvm не сообщает — их след: сетевой журнал и изменения файлов.
- Хранение: `audit.log` (JSON lines, ротация 10 МБ), экспорт в JSONL с кнопки.
- **SIEM**: syslog RFC 5424 (UDP/TCP, сообщение — JSON, facility local0–7) и/или HTTP POST пачек JSON (Splunk HEC, Elastic, Graylog и т.п., заголовок Authorization хранится только на сервере). Сетевые события фильтра — по выбору: только блокировки или все.
- **Оповещения**: N заблокированных соединений одной машины за M секунд → уведомление в интерфейсе, запись в журнал, SIEM и веб-хук (POST JSON с полем `text`).

## Изоляция ИИ-агентов

### Доступ в сеть: allow list (egress-фильтр)

Страница **Доступ в сеть** (`#/egress`). На хосте работает фильтрующий HTTP(S)-прокси smolvm-web (порт `SMOLVM_WEB_EGRESS_PORT`, по умолчанию 7791). Машине с включённым фильтром в `HTTP(S)_PROXY` подставляется адрес этого прокси с её собственным токеном; каждое соединение сверяется с allow list машины и уходит в интернет хоста — через корпоративный прокси, если он настроен, иначе напрямую.

| Что | Как |
|---|---|
| Правила | `api.example.com` — ровно хост; `.example.com` — хост и поддомены; `*.example.com` — только поддомены; `10.0.0.0/8`, `192.0.2.10` — IP; `*` — любой. Порты: `443` (по умолчанию), `443,80`, `8000-8100`, `*`. Можно вставить URL — хост и порт извлекутся. |
| Списки | Именованные наборы правил («Общий», «LLM API», …) с шаблонами: PyPI, npm, GitHub, Docker Hub, apt/apk, Go, crates.io, Hugging Face, OpenAI, Anthropic, DeepSeek, OpenRouter, Gemini. Машина подключает списки и может иметь собственные правила. Отмеченные «подключать к новым машинам» включаются автоматически. |
| Журнал (отдельная страница) | Все соединения (разрешено/заблокировано, правило, трафик, путь — через корп. прокси или напрямую). Заблокированные собираются в блок «Разрешить»: хост или домен целиком добавляется в список или в правила машины одной кнопкой. Файл: `egress.log` в каталоге настроек. |
| Применение | Правила — сразу, без перезапуска. Включение фильтра для существующей машины — сразу для консоли/exec и профиля гостя (profile.d, pip, npm, apt, git), для основного процесса машины — при следующем запуске через smolvm-web (`smolvm machine update --env`). |
| Защита хоста | Адреса хоста, loopback, link-local (169.254.x — metadata), частные сети доступны только по явному правилу IP/CIDR — даже если разрешённое имя на них резолвится; `*` их не открывает. Без токена — 407, с чужих адресов (LAN) — 403. |
| Жёсткая изоляция | Фильтр видят только программы, учитывающие `HTTP(S)_PROXY`. С флажком «Жёстко» smolvm получает egress-политику «только IP хоста» (`allowedCidrs`), так что в обход фильтра наружу не выйти. Применяется при создании или при старте остановленной машины через smolvm-web. Учтите: машине доступны и другие сервисы хоста на внешнем интерфейсе. |
| Образы | Образ при старте качается отдельным токеном, которому дополнительно разрешены реестры (список — в настройках страницы; для Docker Hub это `registry-1.docker.io`, `auth.docker.io` и CDN `production.cloudflare.docker.com`, `production.cloudfront.docker.com`). Если скачивание всё же упрётся в запрет («…: Forbidden»), сообщение при запуске скажет, кто запретил: фильтр smolvm-web или корпоративный прокси. |

Ограничения: HTTPS не расшифровывается — фильтр работает по хосту и порту, не по пути. Машины с подстановкой smolvm (`substitute`) стартуют через API и до фильтра не достают. Если IP хоста сменился, жёсткая политика обновится при следующем запуске.

### Директории и права пользователей

Страница **Директории** (`#/dirs`).

1. **Разрешённые директории хоста** — реестр: имя, путь на хосте, путь в машине, «максимум» (только чтение / чтение и запись) и доступ по умолчанию. Нельзя добавить корень диска, домашнюю директорию целиком, системные пути и места с ключами (`~/.ssh`, `~/.aws`, `~/.kube`, `~/.docker`, настройки smolvm-web…). Каталог настроек smolvm-web (там хранилище секретов) не монтируется никогда, в том числе через поле «Монтирования». **Строгий режим** разрешает в поле «Монтирования» формы создания только директории из реестра в пределах их максимума.
2. **Доступ в машине** — пользователи гостя (создаются автоматически, можно задать uid) и матрица «директория × пользователь»: запись / чтение / нет доступа, плюс «остальные» для всех неперечисленных. Кнопка «Проверить фактические права» выполняет в машине проверку от имени каждого пользователя.

Как обеспечивается:

- **Хост**: каждая директория монтируется в машину до двух раз — представление на запись (если кому-то нужна запись) и read-only представление (если кому-то нужно только чтение). Read-only обеспечивает хост: при «максимуме» «только чтение» не пишет даже root в машине.
- **Гость**: представления лежат в `/.smolvm-dirs/<имя>/{rw,ro}/data` за «шлюзами» — каталогами 0700 с POSIX ACL для нужных пользователей (пакет `acl` ставится в машину автоматически; без него — один пользователь на представление). smolvm exec сбрасывает дополнительные группы, поэтому группы не используются. Путь в машине (`/work`) — ссылка на самое широкое представление; у каждого пользователя есть `~/work` на своё; при наличии записи read-only представление ещё и в `/work-ro`.
- Смена прав внутри уже смонтированных представлений применяется сразу. Новая директория или новое представление требуют перезапуска (кнопка «Перезапустить сейчас»): smolvm меняет монтирования только у остановленной машины, smolvm-web делает это `smolvm machine update --volume` прямо перед стартом.

Ограничения: **root в машине обходит права гостя** — запускайте агентов от обычных пользователей (поле «user» в консоли, `"user"` в API exec). Монтирование сохраняет владельца с хоста: писать может пользователь с uid владельца директории на хосте (UI подсказывает uid). При самом первом запуске шлюзы закрываются сразу после старта, а не до него.

## Безопасность

`smolvm serve` **не имеет аутентификации**: доступ к API = shell на хосте. Поэтому прокси:

- слушает только `127.0.0.1`;
- отклоняет запросы с чужим `Host` (DNS rebinding) и `Origin`;
- требует заголовок `X-Smolvm-UI: 1` для изменяющих запросов.

Настройки (могут содержать пароль прокси) хранятся с правами `0600`. Не публикуйте порт наружу.

Файлы в каталоге настроек: `settings.json`, `state.json`, `vault.enc.json` (секреты), `egress.json` (allow list и токены машин), `dirs.json` (директории и права), `egress.log` (журнал соединений), `audit.json` / `audit.log` (аудит), `review.json` (рабочие копии), `snapshots.json` + `checkpoints/` (снимки), `agents.json`, `smolfile.json`.

## Замечания

- Остановка `smolvm serve` **не останавливает машины**.
- Консоль не интерактивная (нет TTY): для полноценного shell — `smolvm machine exec -it --name <имя> -- sh`.
